# Rust `no_std` 中的 `spin_loop()` 与裸机停机循环

> **学习主题**：`core::hint::spin_loop()`、`loop`、Never Type `!`、`#[entry]`、Semihosting、QEMU、`WFI`、`panic_handler`  
> **适用环境**：Rust `no_std` / `no_main`、ARM Cortex-M、`cortex-m-rt`、QEMU  
> **核心问题**：为什么 `kernel_main()` 和 `panic_handler()` 最后都要保留无限循环？

---

## 一、`core::hint::spin_loop()` 是什么？

你的代码：

```rust
loop {
    core::hint::spin_loop();
}
```

需要分成两个部分理解。

### 1. `loop`：无限循环

```rust
loop {
    // 不断重复
}
```

只要没有 `break`、`return` 或其他控制流转移，程序就会一直循环。

### 2. `spin_loop()`：处理器自旋等待提示

`core::hint::spin_loop()` 是 Rust 提供的 **Spin-wait Hint（自旋等待提示）**。

它告诉处理器：当前代码正在进行自旋等待（Busy-wait），处理器可以根据架构对等待过程进行优化。在某些架构上，编译器会生成专用的提示指令；对于 Cortex-M，可能对应 `YIELD` 等架构提示，具体取决于目标和编译实现。

**注意：**

- `spin_loop()` 本身不是无限循环；
- 不会让程序退出；
- 不保证 CPU 睡眠；
- 不会主动让出操作系统线程的执行权；
- 单独调用一次，之后程序仍会继续向下执行。

因此：

```rust
core::hint::spin_loop(); // 提示一次，然后继续执行
```

和：

```rust
loop {
    core::hint::spin_loop(); // 不断自旋
}
```

不是一回事。

## 二、为什么 `kernel_main()` 最后要有无限循环？

原代码：

```rust
#[entry]
fn kernel_main() -> ! {
    // ... 执行任务 ...

    debug::exit(debug::EXIT_SUCCESS);

    loop {
        core::hint::spin_loop();
    }
}
```

关键是返回类型：

```rust
fn kernel_main() -> !
```

`!` 称为 **Never Type（永不返回类型）**，表示该函数不会正常返回给调用方。

### 1. 操作系统程序的退出

```rust
fn main() {
    println!("Hello");
}
```

在 Windows、Linux 等环境中，可以大致理解为：

```text
操作系统启动程序
      ↓
运行时调用 main()
      ↓
执行程序逻辑
      ↓
main() 返回
      ↓
运行时通知操作系统程序结束
      ↓
操作系统回收进程资源
```

### 2. Cortex-M 裸机程序的情况

你使用：

```rust
#![no_std]
#![no_main]

use cortex_m_rt::entry;

#[entry]
fn kernel_main() -> ! {
    // ...
}
```

裸机程序通常没有操作系统在 `main()` 返回后接管执行。启动过程大致是：

```text
MCU 上电 / 复位
      ↓
cortex-m-rt 的 Reset Handler
      ├── 建立启动执行环境
      ├── 初始化 .data
      └── 清零 .bss
      ↓
调用 kernel_main()
      ↓
执行程序逻辑
      ↓
任务结束
      ↓
接下来怎么办？
```

`cortex-m-rt` 的 `#[entry]` 要求入口函数返回 `!`，即不能正常返回。

**所以最后需要一个永不返回的执行路径。**

但 `!` 并不要求必须写 `loop`：任何不会正常返回的执行路径都可以满足它；无限循环只是最简单直观的方式。

## 三、`debug::exit()` 不是已经退出了吗？

原代码：

```rust
use cortex_m_semihosting::debug;

println!("Done, exiting QEMU.");

debug::exit(debug::EXIT_SUCCESS);

loop {
    core::hint::spin_loop();
}
```

这里的 `debug::exit()` 依赖 **Semihosting（半主机机制）**。

Semihosting 允许裸机程序通过特殊的调试调用，请求调试器或模拟器提供服务。

```rust
debug::exit(debug::EXIT_SUCCESS); // 请求报告成功退出
debug::exit(debug::EXIT_FAILURE); // 请求报告失败退出
```

### 情况 A：QEMU 支持并处理退出请求

```text
kernel_main()
      ↓
debug::exit(EXIT_SUCCESS)
      ↓
QEMU 处理请求
      ↓
模拟运行结束
```

在这种情况下，最后的无限循环通常不会执行。

### 情况 B：真实 Cortex-M 开发板

真实 MCU 通常没有一个可以直接“退出”的宿主进程。如果调试调用返回，后面的循环就是兜底路径：

```text
kernel_main()
      ↓
debug::exit(...)
      ↓
如果调用返回
      ↓
loop { spin_loop() }
      ↓
主执行流程不再向后推进
```

**重要提醒：** 在没有 Semihosting 调试器支持的真机上，`debug::exit()` 不一定只是“无效”。它可能使用 `BKPT` 等调试陷入指令，从而触发 HardFault 或其他异常。因此正式部署时应区分 QEMU 和真实硬件代码。

## 四、无限循环是否等于 CPU 真正停机？

**不完全等于。**

```rust
loop {
    core::hint::spin_loop();
}
```

表示主执行流程一直循环，但 CPU 仍可能持续执行指令，并消耗功耗。

### 三种常见写法

**1. 简单无限循环**

```rust
loop {}
```

编译器可生成与之等价的循环代码。

**2. 自旋等待**

```rust
loop {
    core::hint::spin_loop();
}
```

持续自旋，并提供处理器提示。常用于短时间轮询或自旋锁等待，并不是低功耗睡眠。

**3. 等待中断**

```rust
loop {
    cortex_m::asm::wfi();
}
```

`wfi()` 是 ARM 的 **Wait For Interrupt（等待中断）** 指令，通常允许处理器进入等待中断的低功耗状态。中断或其他允许的唤醒事件可能让处理器继续执行，然后再次进入等待。

| 写法 | CPU 典型行为 | 常见用途 |
|---|---|---|
| `loop {}` | 无限循环 | 最简单的永不返回路径 |
| `loop { spin_loop(); }` | 持续自旋，提供提示 | 短时轮询、自旋等待 |
| `loop { wfi(); }` | 等待中断，通常可降低空闲功耗 | 裸机空闲循环 |

`spin_loop()` 不会自动禁止中断，因此即使主程序一直自旋，只要中断未被屏蔽并且系统允许响应，中断处理程序仍可能运行。

“主执行流程不再向后推进”和“整个 MCU 完全停止工作”是两回事。

## 五、为什么 `panic_handler` 中也要有无限循环？

原代码：

```rust
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    debug::exit(debug::EXIT_FAILURE);

    loop {
        core::hint::spin_loop();
    }
}
```

`panic_handler` 的返回类型也是 `!`，不能正常返回。

其执行逻辑是：

```text
程序发生 panic
      ↓
进入 panic_handler
      ↓
debug::exit(EXIT_FAILURE)
      ├── QEMU 成功处理：模拟结束
      └── 调试退出请求返回
                  ↓
          loop { spin_loop() }
                  ↓
          不返回发生 panic 的代码
```

这个无限循环的作用：

1. 保证 panic 处理路径不会正常返回。
2. 如果退出请求返回，程序仍然有明确的兜底执行路径。

不过，这并不意味着中断和硬件活动都自动停止；是否继续运行还取决于中断屏蔽状态及系统配置。

## 六、如何兼容 QEMU 和真实开发板？

如果当前主要使用 QEMU 学习，但将来希望移植到真实 Cortex-M 开发板，可以通过 **Cargo feature + 条件编译** 区分两种环境。

### 1. 在 `Cargo.toml` 中定义 feature

```toml
[features]
qemu = []
```

### 2. 在 Rust 中使用条件编译

```rust
// 仅启用 qemu feature 时请求模拟器退出
#[cfg(feature = "qemu")]
debug::exit(debug::EXIT_SUCCESS);

// 真机环境或退出请求返回时，进入等待中断循环
loop {
    cortex_m::asm::wfi();
}
```

效果：

- **QEMU 环境**：启用 `qemu` feature，通过 Semihosting 请求结束模拟。
- **真实开发板**：不启用该 feature，避免无条件执行不受支持的 Semihosting 调用。
- **兜底路径**：主函数不会正常返回，而是进入空闲等待循环。

`panic_handler` 中的失败退出也可以采用同样的条件编译处理。

如果当前目的就是学习自旋行为，继续保留 `spin_loop()` 也完全可以。

## 七、结合前面学过的 `no_std`、静态 Arena 与堆分配器

把整个程序串起来，可以得到以下运行模型：

```text
MCU 上电 / 复位
      ↓
Reset Handler
      ├── 建立启动执行环境
      ├── 初始化 .data
      └── 清零 .bss
      ↓
kernel_main() -> !
      |
      ├── 使用 core 中的固定容量数据结构
      |
      ├── 使用 alloc 的 Vec、String、Box
      |         |
      |         v
      |     GlobalAlloc
      |         |
      |         v
      |     静态 Arena 内存池
      |
      ├── 执行业务逻辑
      |
      v
任务执行完毕
      |
      ├── QEMU：通过 Semihosting 请求退出
      |
      └── 真实 MCU：进入空闲循环
                         |
                         v
                    spin_loop / WFI
```

在实际嵌入式程序中，程序往往不会像桌面命令行工具那样“做完一次就退出”。很多裸机程序采用 **Superloop（主循环）**，持续处理外设、事件和状态；另一些系统使用 RTOS 来调度任务。

你当前的代码属于教学演示：执行一系列操作、打印结果，然后在 QEMU 中请求退出。为了保证入口函数永不正常返回，仍然保留了无限循环。

## 八、最终总结

| 概念 | 核心含义 |
|---|---|
| `loop` | 让控制流持续循环 |
| `core::hint::spin_loop()` | 向 CPU 提示当前正在自旋等待，不保证睡眠 |
| `cortex_m::asm::wfi()` | Cortex-M 等待中断，通常适合低功耗空闲 |
| `-> !` | 函数不会正常返回 |
| `#[entry]` | 定义 Cortex-M 裸机入口，要求入口函数永不正常返回 |
| `debug::exit()` | 通过 Semihosting 请求调试宿主或模拟器退出 |
| `#[panic_handler]` | 定义 `no_std` 环境的 panic 处理入口 |

**一句话结论：**

> 你代码最后的无限循环，本质上是为了满足裸机入口函数永不返回的要求，并在 Semihosting 退出请求返回时提供兜底路径。`spin_loop()` 只是循环内部的一种处理器等待提示，不等于 CPU 睡眠；如果希望在 Cortex-M 上实现低功耗空闲等待，可以根据系统条件考虑 `WFI`。

**下一步可以继续研究的问题：**

> 既然 `kernel_main()` 不会正常返回，那么实际嵌入式固件是否通常一直运行在一个主循环中？主循环（Superloop）、中断驱动和 RTOS 任务调度有什么区别？
