# 从 Rust 源代码到 Cortex-M 机器码：LLVM、ELF 与裸机启动流程

> **Rust `no_std` 学习笔记 · 编译器与编译产物篇**  
> 主题：LLVM、`rustc`、ELF、`llvm-objdump`、内存段、链接脚本、中断向量表、Reset Handler、`no_std`  
> 示例环境：Rust `no_std` + `cortex-m-rt` + QEMU `lm3s6965evb`  
> 整理日期：2026-10-27

---

## 0. 先看结论

1. **LLVM 是一套编译器基础设施**：Rust 编译器通常借助 LLVM 优化程序并生成目标 CPU 的机器码。
2. **`llvm-objdump` 是分析工具，不是编译器本身**：它能查看目标文件的格式、节、符号、机器指令等。
3. **ELF 是编译/链接产物的一种文件格式**：它描述机器代码、数据、地址、符号和装载信息。
4. **Cortex-M 复位时从中断向量表获取初始栈指针和 Reset Handler 地址**，不能简单理解为“CPU 直接从 ELF 头的入口地址开始运行”。
5. **`0x00000401` 中的最低位 `1` 表示 Thumb 状态**；对应的 Reset 指令位于 `0x00000400`。
6. **`.bss` 中可以放置静态 `Arena` 数组**：虽然它存放在静态 RAM 中，分配器仍可将其作为“堆内存池”动态分配。
7. **`no_std` 不是“不使用任何库”**：仍可以使用 `core`、`alloc`、自定义全局分配器和硬件/调试输出。
8. **仅搜索符号表中是否有 `std` 字符串，不能严格证明程序没有依赖标准库**。

## 1. LLVM 是什么？

LLVM 最初来自 *Low Level Virtual Machine* 这一名称，如今通常指一整套**编译器基础设施项目**，包含中间表示、优化器、机器码生成后端以及二进制分析工具等。

例如 Rust 源代码：

```rust
fn add(a: u32, b: u32) -> u32 {
    a + b
}
```

CPU 并不直接理解 Rust 源代码，它需要与自身指令集匹配的机器指令。LLVM 是这一转换过程中的重要组成部分。

### 1.1 Rust 程序的典型编译流程

```text
Rust 源代码
  main.rs / heap.rs / logbuf.rs ...
        |
        v
rustc 前端
  语法分析、类型检查、借用检查、MIR 等
        |
        v
LLVM 后端（典型配置）
  LLVM IR、优化、指令选择、机器码生成
        |
        v
链接器
  合并目标文件，按照 link.x / 内存布局安排地址
        |
        v
ELF 文件
  target/<target-triple>/debug/nostd-bin
        |
        v
QEMU / Cortex-M
  加载程序、执行机器指令
```

**三个名字不要混淆：**

| 名称 | 主要职责 |
|---|---|
| `rustc` | Rust 编译器，负责 Rust 语言语义检查并驱动代码生成 |
| LLVM | 提供中间表示、优化和机器码生成等能力 |
| `llvm-objdump` | 分析已经生成的目标文件、ELF、节、符号和汇编指令 |

补充：LLVM 是 Rust 常用的代码生成后端，但不是理论上唯一可用的后端。

## 2. 什么是 ELF？

运行：

```bash
llvm-objdump -f target/thumbv7em-none-eabihf/debug/nostd-bin
```

示例输出：

```text
target/thumbv7em-none-eabihf/debug/nostd-bin:
file format elf32-littlearm
architecture: arm
start address: 0x00000401
```

**ELF（Executable and Linkable Format）** 是一种可执行文件与可链接文件格式。

它可以包含：

- 机器指令；
- 数据；
- 节（section）与装载段（segment）；
- 地址和入口信息；
- 符号表；
- 调试信息等。

### 2.1 三个输出字段的含义

| 字段 | 含义 |
|---|---|
| `elf32-littlearm` | 32 位 ARM、小端字节序的 ELF |
| `architecture: arm` | 目标机器架构为 ARM |
| `start address: 0x00000401` | ELF 头记录的入口地址 |

### 2.2 为什么入口是 `0x401` 而不是 `0x400`？

Cortex-M 执行 Thumb 指令集。函数入口地址表示中的最低位 `1` 用于表示 Thumb 状态。

```text
Reset Handler 的实际指令位置：0x00000400
用于表示 Thumb 入口的地址：  0x00000401
                                     ^
                                     |
                                 Thumb 状态位
```

**不能理解成 CPU 从奇数地址 `0x401` 开始取第一条指令。**

更重要的是：**Cortex-M 硬件复位主要依靠中断向量表来获得初始 MSP 和 Reset Handler 地址**。ELF 头里的入口字段是链接产物的元信息，不能代替 Cortex-M 的硬件复位机制。

## 3. `llvm-objdump -h`：查看 ELF 节布局

运行：

```bash
llvm-objdump -h target/thumbv7em-none-eabihf/debug/nostd-bin
```

示例输出（摘录）：

```text
Idx Name           Size       VMA        Type
 1  .vector_table  00000400   00000000   DATA
 2  .text          0000743c   00000400   TEXT
 3  .rodata        00002dd4   0000783c   DATA
 4  .data          00000000   20000000   DATA
 6  .bss           000040a0   20000000   BSS
```

- **Size**：节大小，十六进制。
- **VMA**：*Virtual Memory Address*，节的运行地址。在此类无普通进程虚拟地址空间的裸机目标上，可以结合 MCU 内存映射理解为安排的运行地址。
- **Type**：`objdump` 展示的节类型标签。`.rodata` 显示为 `DATA` 并不意味着它可写。

### 3.1 这次程序的内存布局示意

```text
程序映射区域（通常是 Flash/ROM 映射）
0x00000000  +---------------------------+
            | .vector_table            |
            | 0x400 B = 1024 B         |
0x00000400  +---------------------------+
            | .text                     |
            | 0x743c B ≈ 29.1 KiB      |
            | 程序机器指令              |
0x0000783C  +---------------------------+
            | .rodata                   |
            | 0x2dd4 B ≈ 11.5 KiB      |
            | 字符串等只读数据          |
0x0000A610  +---------------------------+

SRAM / 可写存储区域
0x20000000  +---------------------------+
            | .bss                      |
            | 0x40a0 B = 16544 B       |
            | 包含静态 Arena 16 KiB     |
0x200040A0  +---------------------------+
            | 其他可用 RAM / 栈空间等   |
            | 实际规划由链接脚本决定    |
0x20010000  +---------------------------+
            | 初始栈顶 _stack_start     |
            +---------------------------+
```

> 这是基于输出整理的逻辑示意图，不是完整的芯片物理内存地图，也不是按地址比例绘制。

### 3.2 `.vector_table`：中断向量表

起始地址为 `0x00000000`，大小为 `0x400 = 1024` 字节。

对于典型 Cortex-M 启动过程，最重要的前两个表项是：

```text
0x00000000：初始 MSP（主栈指针）
0x00000004：Reset Handler 地址
```

结合后面的符号输出，预期它们对应：

```text
初始 MSP：0x20010000
Reset：   0x00000401
```

`cortex-m-rt` 提供启动支持，链接脚本负责将向量表安排到相应位置。

### 3.3 `.text`：机器指令

```text
.text  0000743c  00000400
```

说明 `.text` 从 `0x00000400` 开始，大小为 `0x743c` 字节。

你写的 `kernel_main()`、Bump Allocator 代码及其他最终保留的函数，通常会编译为这里的机器指令。

### 3.4 `.rodata`：只读数据

```text
.rodata  00002dd4  0000783c
```

例如：

```rust
println!("Hello, no_std!");
```

字符串字面量的字节通常存储在只读数据中；执行打印逻辑的机器指令则通常位于 `.text`。

### 3.5 `.data`：需要可写存储的已初始化静态数据

```text
.data  00000000  20000000
```

这次输出中 `.data` 大小为 0。

在常见裸机程序中，`.data` 可以用于存放需要在 RAM 中运行、且具有初始内容的静态数据；启动代码会根据链接布局进行必要的初始化或拷贝。

### 3.6 `.bss`：通常用于零初始化静态存储

```text
.bss  000040a0  20000000
```

十六进制换算：

```text
0x40a0 = 16544 B
16 KiB = 16384 B
差额 = 160 B
```

你的 Bump Allocator：

```rust
const HEAP_SIZE: usize = 16 * 1024;

#[repr(align(16))]
struct Arena(UnsafeCell<[u8; HEAP_SIZE]>);

#[global_allocator]
static ALLOCATOR: Bump = Bump::new();
```

因此，**16 KiB 的静态数组可以位于 `.bss`，而整个 `.bss` 大小约为 16 KiB + 160 B**。

剩余的 160 B 可能包含其他静态对象、分配器统计字段、对齐填充等。**仅凭 `.bss` 总大小，不能精确断言这 160 B 分别由哪些对象构成**；要进一步核对，需要查看相关符号及链接 map 文件。

这与前面讨论的概念完全一致：

> `Arena` 本身具有静态存储期，通常占用静态 RAM；它被 `GlobalAlloc` 切分并分配给 `Box`、`Vec` 等调用方，所以它仍然是一个有效的“堆内存池”。

## 4. `llvm-objdump -t`：查看符号表

运行：

```bash
llvm-objdump -t target/thumbv7em-none-eabihf/debug/nostd-bin
```

示例关键符号：

```text
00000400 g F .text 00000044 Reset
00005880 g F .text 00000000 DefaultHandler
00001d8a g F .text 00000008 main
20010000 g   *ABS* 00000000 _stack_start
20000000 g   .bss  00000000 __sbss
200040a0 g   .bss  00000000 __ebss
```

| 符号 | 地址 | 作用 |
|---|---|---|
| `Reset` | `0x00000400` | 复位处理函数 |
| `DefaultHandler` | `0x00005880` | 默认异常/中断处理入口 |
| `main` | `0x00001D8A` | `#[entry]` 机制导出的应用入口符号 |
| `_stack_start` | `0x20010000` | 初始栈顶 |
| `__sbss` | `0x20000000` | `.bss` 起点 |
| `__ebss` | `0x200040A0` | `.bss` 终点 |

### 4.1 `Reset` 与 `main` 的区别

你的源代码：

```rust
#[entry]
fn kernel_main() -> ! {
    // ...
}
```

经 `cortex-m-rt` 的入口机制关联到导出的 `main` 符号。

但 CPU 复位时**先进入 `Reset`**，而不是直接执行你的 `kernel_main()`：

```text
CPU 复位
   |
   v
向量表中的 Reset Handler
   |
   v
cortex-m-rt 启动逻辑
   |-- 初始化 .data
   |-- 清零 .bss
   |-- 建立必要运行环境
   v
main（对应 kernel_main）
```

准确地说，复位后执行的第一条指令位于 **Reset Handler 的机器代码中**，而不是说符号 `Reset` 本身就是“一条指令”。

### 4.2 为什么 `_stack_start` 在高地址？

Cortex-M 栈通常向低地址增长。

```text
较高地址
0x20010000  <- 初始栈顶
       |
       v  栈向低地址增长
       |
       |
0x200040A0  <- .bss 结束
0x20000000  <- .bss 开始
较低地址
```

必须通过链接布局和运行时设计避免栈与静态数据或堆区域重叠。

## 5. 如何检查程序是否依赖 `std`？

原先的检查思路：

```bash
llvm-objdump -t target/thumbv7em-none-eabihf/debug/nostd-bin | findstr std
```

有两个需要修正的地方。

### 5.1 WSL2/Linux 中使用 `grep`

你现在是在 WSL2 的 Linux 终端中，通常使用：

```bash
llvm-objdump -t -C target/thumbv7em-none-eabihf/debug/nostd-bin | grep 'std::'
```

其中：

- `-t`：显示符号表；
- `-C`：尝试反修饰符号名称；
- `grep 'std::'`：筛选看起来属于 `std` 命名空间的符号。

### 5.2 没搜到 `std`，不等于严格证明没有使用 `std`

原因包括：

- 你的 crate 名称 `nostd_bin` 自身包含 `std` 字符串，因此直接 `grep std` 可能产生误判；
- 符号名称可能经过修饰；
- 优化、裁剪或符号剥离可能让部分名称不可见；
- 符号表文本搜索不是严格的依赖分析方法。

可以辅助查看 Cargo 依赖树：

```bash
cargo tree -p nostd-bin --target thumbv7em-none-eabihf
```

但 Cargo 依赖树也不是对 sysroot 中 `core` / `alloc` / `std` 的完整逐符号证明。

对于你的程序，关键是：

```rust
#![no_std]
```

它使 crate 不再隐式链接和导入标准库 `std` 的常规 prelude，而是依赖 `core`，并在需要动态分配时显式引入：

```rust
extern crate alloc;

use alloc::boxed::Box;
use alloc::string::String;
use alloc::vec::Vec;
```

### 5.3 为什么 `no_std` 仍能打印、分配、格式化？

| 能力 | 在你的程序中来自哪里 |
|---|---|
| 基础类型、`Layout`、原子操作 | `core` |
| `Vec`、`Box`、`String`、`format!` | `alloc` |
| 动态分配的后备存储 | 你实现的 `GlobalAlloc` / 静态 Arena |
| 输出文本 | 自定义 console 或 Semihosting 等机制 |
| 启动入口与向量表 | `cortex-m-rt` |
| 程序实际执行 | QEMU 或 Cortex-M 硬件 |

**`no_std` 的重点不是“不能使用库”，而是“不依赖标准库默认提供的操作系统运行环境”。**

## 6. 继续深入：直接看 ARM 汇编与向量表原始字节

### 6.1 反汇编整个 ELF

```bash
llvm-objdump -d target/thumbv7em-none-eabihf/debug/nostd-bin
```

`-d` 会把机器指令反汇编为 ARM/Thumb 汇编，便于观察程序最终变成了什么指令。

### 6.2 只看 `Reset` 附近

```bash
llvm-objdump -d \
  --start-address=0x400 \
  --stop-address=0x450 \
  target/thumbv7em-none-eabihf/debug/nostd-bin
```

可以观察 `Reset` 入口附近的指令。

### 6.3 查看中断向量表的原始字节

```bash
llvm-objdump -s -j .vector_table \
  target/thumbv7em-none-eabihf/debug/nostd-bin
```

因为是**小端**格式，若前两个表项分别为：

```text
初始 MSP = 0x20010000
Reset    = 0x00000401
```

那么它们在文件中按字节排列的典型形式是：

```text
00 00 01 20   01 04 00 00
|----------|  |----------|
 初始 MSP      Reset 地址
```

这是一个非常值得亲自验证的实验：**从原始字节反推出 CPU 上电后会使用的栈顶和复位入口。**

### 6.4 如果系统找不到 `llvm-objdump`

可以根据安装方式检查 LLVM 工具链，例如：

```bash
command -v llvm-objdump
llvm-objdump --version
```

Rust 工具链也可以安装 LLVM 工具组件：

```bash
rustup component add llvm-tools-preview
```

但 `llvm-tools-preview` 安装后不一定会自动在 `PATH` 中提供名为 `llvm-objdump` 的命令；可以通过相应路径调用，或安装系统 LLVM 工具 / `cargo-binutils` 配套工具。

## 7. 你当前 QEMU 目标还有一个兼容性问题

你的 QEMU 机器是：

```text
-machine lm3s6965evb
```

该机器模拟 **Cortex-M3**。

而之前编译目标是：

```text
thumbv7em-none-eabihf
```

它适合 ARMv7E-M 且采用硬件浮点 ABI 的目标，例如相应的 Cortex-M4F 环境。

对于 `lm3s6965evb`，更匹配的 Rust target 是：

```text
thumbv7m-none-eabi
```

可以安装：

```bash
rustup target add thumbv7m-none-eabi
```

并同步修改 Cargo 的 `--target`、rust-analyzer 的目标配置，以及后续 `objdump` 所读取的输出路径。

**注意：本笔记前面的 ELF 地址、节大小和符号值均来自你原先的 `thumbv7em-none-eabihf` 编译结果；更换 target 后，应重新编译并重新检查，不要假定数值完全相同。**

## 8. 把之前的知识全部串起来

```text
Rust 源代码
  |
  |  语法 / 类型 / 借用检查
  v
rustc
  |
  |  LLVM 优化与机器码生成
  v
目标文件 / 机器指令
  |
  |  链接脚本 link.x
  |  安排 .vector_table / .text / .rodata / .data / .bss
  v
ELF 文件
  |
  |  QEMU 加载或烧录到 MCU
  v
Cortex-M 复位
  |
  |  读取向量表：初始 MSP + Reset Handler
  v
Reset Handler（cortex-m-rt）
  |
  |  初始化 .data / .bss 等
  v
main（你的 kernel_main）
  |
  |  core：无需动态分配的基础能力
  |  alloc：Vec / Box / String 等
  |  GlobalAlloc：使用静态 Arena 作为堆池
  v
程序运行
  |
  +-- QEMU：Semihosting 请求退出
  |
  +-- 真机：持续主循环 / 等待中断
```

### 最后记住三个层次

1. **编译器层**：Rust 源码如何经过 `rustc` / LLVM 变成机器码。
2. **链接与内存层**：ELF 中的代码和数据如何映射到 Flash、RAM 和具体地址。
3. **硬件启动层**：Cortex-M 如何通过向量表找到栈顶与 Reset Handler，最终运行你的 `kernel_main()`。

理解这三个层次后，你就能从一份 Rust `no_std` 源码，追踪到它在 MCU 内存中占据的位置，以及 CPU 如何真正开始执行它。
