## 0. 先记住这 10 条核心结论

1. **`[u8; N]` 只描述数组类型与大小，不决定它放在栈、堆还是静态存储区。**
2. **`static ALLOCATOR: Bump` 让整个 `Bump` 实例具有静态存储期**；内部 `Arena`、`UnsafeCell`、数组和原子字段都嵌在这个实例里，并不会各自再分配一份内存。
3. **`#[global_allocator]` 是注册全局分配器，不是「把 `Arena` 放到堆上」的指令。**
4. **你已经实现了真正有意义的简易堆分配器**：它把一块静态 RAM 缓冲区作为可动态分配的内存池。裸机「堆」首先是一种管理约定，不要求一定来自操作系统或专门的 `.heap` 段。
5. **对齐约束的是实际地址**：`address % alignment == 0`；栈、静态对象、堆分配都要遵守。
6. **`#[repr(align(16))]` 只保证至少 16 字节对齐**；若 `Layout` 请求 32、64 等更高对齐，不能仅把相对偏移量按该值对齐，必须考虑 `Arena` 的实际基地址。
7. **`repr(C)`、`repr(transparent)`、`repr(align(N))` 影响类型布局或 ABI，不决定存储区域。**
8. **真实开发板可以用链接脚本保留指定 RAM 区间作为堆**；分配器只需管理该区间的起始地址、容量和分配状态。
9. **`const fn` 是「允许在常量求值上下文中调用」**，不是「每次调用都必定在编译期执行」；你的 `Bump::new()` 之所以需要它，是因为要初始化 `static ALLOCATOR`。
10. **并发安全不仅取决于原子偏移量**：CAS 保证分配区间不重叠；调用方仍须遵守指针、别名和线程同步规则。`UnsafeCell` 本身并不自动保证线程安全。

## 1. 讨论起点：这个 Bump Allocator 在做什么？

原始设计的关键结构如下（节选）：

```rust
use core::alloc::{GlobalAlloc, Layout};
use core::cell::UnsafeCell;
use core::sync::atomic::{AtomicUsize, Ordering};

const HEAP_SIZE: usize = 16 * 1024;

#[repr(align(16))]
struct Arena(UnsafeCell<[u8; HEAP_SIZE]>);

unsafe impl Sync for Arena {}

struct Bump {
    arena: Arena,
    offset: AtomicUsize,
    count: AtomicUsize,
    peak: AtomicUsize,
}

impl Bump {
    const fn new() -> Self {
        Self {
            arena: Arena(UnsafeCell::new([0; HEAP_SIZE])),
            offset: AtomicUsize::new(0),
            count: AtomicUsize::new(0),
            peak: AtomicUsize::new(0),
        }
    }
}

#[global_allocator]
static ALLOCATOR: Bump = Bump::new();
```

**职责拆分：**

| 元素 | 实际职责 | 不负责什么 |
|---|---|---|
| `[u8; HEAP_SIZE]` | 提供 16 KiB 的实际字节存储 | 不决定存储在堆上 |
| `UnsafeCell` | 允许经共享访问路径取得内部可变存储的原始指针 | 不负责分配，也不自动提供线程安全 |
| `Arena` | 包装字节数组并提高其对齐要求 | 不自动产生独立内存 |
| `static ALLOCATOR` | 创建静态存储期的 `Bump` 实例 | 不等于动态堆分配 |
| `#[global_allocator]` | 让 Rust 全局分配机制使用该实现 | 不会把实例搬到堆 |
| `offset` | 记录已占用的末端偏移 | 不回收旧分配 |
| `count` | 统计成功分配次数 | 不表示当前存活对象数 |
| `peak` | 记录历史最高占用偏移 | 不是当前对象实际有效载荷大小 |
| `GlobalAlloc::alloc` | 按 `Layout` 返回内存池内一段可用区域 | 不负责初始化用户对象的值 |
| `GlobalAlloc::dealloc`（空实现） | 不回收空间 | 不会让已释放区间再次可用 |

同一个最终程序通常只能注册**一个** `#[global_allocator]`；它负责全局分配接口，不意味着程序中的所有内存都必须经它申请。

Bump 的典型流程：

```text
调用方申请 Layout { size, align }
            |
            v
读取 offset 和 Arena 基地址
            |
            v
计算满足对齐要求的起点 start
            |
            v
计算 end = start + size，检查边界和溢出
            |
            v
CAS(offset: current -> end)
   | 成功                 | 失败
   v                      v
独占 [start, end)       更新 current 并重试
   |
   v
更新统计值，返回指向 Arena 内部的指针
```

## 2. 类型、对象、存储位置和内存管理：四件不同的事

### 2.1 类型声明不会自动分配运行时内存

```rust
struct Foo {
    data: [u8; 1024],
}
```

它只是定义一种布局。是否需要实际存储、存储在哪里，取决于**值如何创建、持有和使用**。

```rust
let local = Foo { data: [0; 1024] };      // 通常是栈上的局部值
static GLOBAL: Foo = Foo { data: [0; 1024] }; // 静态存储期
// Box::new(Foo { ... })                  // 在有可用分配器时申请动态存储
```

局部变量「通常在栈上」是实用的抽象：编译器也可能将值放在寄存器中，或优化掉实际存储。不能仅凭 `let` 断言每个值都必然占用栈内存。

### 2.2 当前 `Arena` 实际在哪里？

因为：

```rust
#[global_allocator]
static ALLOCATOR: Bump = Bump::new();
```

`ALLOCATOR` 具有静态存储期。其内部字段是**内联嵌套**的：

```text
静态存储期的 ALLOCATOR: Bump
|
+-- arena: Arena
|   +-- UnsafeCell<[u8; 16384]>
|       +-- 真正的 16 KiB 字节数组
|
+-- offset: AtomicUsize
+-- count:  AtomicUsize
+-- peak:   AtomicUsize
```

这里是**逻辑包含关系**，不是字段在内存中的精确先后顺序；`Bump` 使用默认 Rust 布局，不能擅自假定字段偏移。

- `Arena` 不是单独在栈上。
- `UnsafeCell` 也不是单独在栈上。
- 这两个包装层不自动触发新的堆分配。
- 对于常见裸机目标，可写静态对象通常被链接到 RAM；具体地址和段由链接脚本与目标平台决定。

### 2.3 为什么「静态数组」也能作为堆？

要区分**物理内存的来源**和**逻辑上的分配用途**。

```text
物理来源：MCU SRAM
    |
    +-- 作为静态变量保存的 16 KiB 数组
             |
             +-- Bump::alloc 动态切分、返回指针
                      |
                      +-- 对调用方而言，这是堆分配得到的内存
```

所以，这个实现**不是“假堆”**。它是一个使用静态存储作后备内存的简易堆分配器。

`#[global_allocator]` 只是将这套分配策略接入 Rust 的全局分配接口。`Box`、`Vec` 等类型在实际需要动态分配时可调用它；编译器也可能优化掉某些分配，不能把每个源代码层面的 `Box` 都当作一次必然发生的分配器调用。

### 2.4 栈、静态存储、堆的区别

| 维度 | 栈（典型情况） | 静态存储 | 堆 / 动态分配 |
|---|---|---|---|
| 谁决定对象位置 | 编译器与调用约定 | 编译器、链接器、启动代码 | 分配器 |
| 常见生命周期 | 函数调用或局部作用域 | 程序整个运行期 | 由申请/释放行为管理 |
| 是否必须是特殊物理 RAM | 否 | 否 | 否 |
| 是否必须使用 `Box` | 否 | 否 | 否 |
| 是否必须满足对齐 | 是 | 是 | 是 |

**最关键的认识：堆并不是 MCU 内部天然标有“Heap”的一类硬件存储器，而是软件选择并管理的一段可用内存。**

## 3. 内存对齐：究竟约束什么，为什么需要？

### 3.1 定义

一个类型或 `Layout` 的对齐值为 `A` 时，存储起始地址必须满足：

$$
\text{address} \bmod A = 0
$$

在 Rust 的 `Layout` 中，`align()` 是**非零的 2 的幂**，所以通常可使用位运算进行向上对齐。

常见平台上的示例（实际要求由目标决定）：

| 类型 | 常见对齐 |
|---|---:|
| `u8` | 1 字节 |
| `u16` | 2 字节 |
| `u32` | 4 字节 |
| `u64` | 8 字节 |

例如对齐要求为 8：

```text
0x1000 -> 满足（4096 % 8 == 0）
0x1003 -> 不满足
0x1008 -> 满足
```

### 3.2 为什么需要对齐？

- **硬件约束**：某些架构/指令不允许特定未对齐访问，或需要额外处理。
- **性能**：未对齐访问在一些平台上可能更慢。
- **Rust 类型与引用契约**：即使硬件能够执行未对齐访问，也不能据此创建不满足对齐要求的普通 Rust 引用。

如果确实要访问未对齐数据，应采用适用的原始指针未对齐读写接口，例如 `read_unaligned` / `write_unaligned`，而不是先创建未对齐的普通引用。

### 3.3 “分配 13 B，后面还剩 3 B”如何理解？

假设初始地址为 `0x1000`，先申请 13 字节：

```text
0x1000                    0x100D        0x1010
|-------- 13 B ----------|--- 3 B ----|
                         ^             ^
                      当前末端      下一个 4B 对齐地址
```

- 如果下一次申请要求 **4 字节对齐**，就必须跳过这 3 字节填充。
- 如果下一次申请要求 **1 字节对齐**，则可以直接从 `0x100D` 开始。

因此：**填充并不是“堆特有”的现象，也不是那 3 字节天生不可用；它取决于下一次分配的对齐要求。**

栈上的局部变量也同样需要对齐。差别主要在于：栈帧通常由编译器安排，堆区域由分配器安排。

### 3.4 `repr(align(16))` 到底保证了什么？

```rust
#[repr(align(16))]
struct Arena(UnsafeCell<[u8; HEAP_SIZE]>);
```

保证：**每个实际存储的 `Arena` 值的起始地址至少按 16 字节对齐。**

它不意味着：
- `Arena` 一定在堆上；
- 内部每一个字节的地址都满足 16 字节对齐；
- 可以安全地满足任意大于 16 的 `Layout.align()`；
- 外层包装会自动额外分配一块内存。

类型大小还可能因对齐要求而增加尾部填充；对这个具体的 16 KiB 数组而言，其长度本身就是 16 的倍数。

### 3.5 原实现中必须修正的对齐问题

原先思路类似：

```rust
let start = align_up(current, align);
return base_ptr.add(start);
```

但 `current` 是**相对偏移量**，`align` 要求的是**最终绝对地址**。

仅在 `base` 已满足所请求的 `align` 时，对偏移量向上对齐才等价于对绝对地址向上对齐。

**反例：**

```text
Arena 基地址 base = 0x1010  （16B 对齐，但不是 32B 对齐）
current         = 1
align           = 32

错误算法：
    align_up(1, 32) = 32
    返回地址 = 0x1010 + 32 = 0x1030
    0x1030 % 32 = 16 -> 不满足 32B 对齐

正确算法：
    current_addr = 0x1010 + 1 = 0x1011
    aligned_addr = align_up(0x1011, 32) = 0x1020
    start        = 0x1020 - 0x1010 = 16
    返回地址     = 0x1020 -> 满足 32B 对齐
```

正确顺序：

1. 计算 `current_addr = base_addr + current`；
2. 对 `current_addr` 进行绝对地址向上对齐；
3. 将对齐后的地址减去 `base_addr`，得到 `start`；
4. 计算 `end = start + size`，检查边界；
5. CAS 预留 `[start, end)`；
6. **通过原始 `base_ptr` 加偏移得到返回指针**，不要简单地把整数地址强转成新指针来代替原指针。

所有加法与边界计算都要考虑整数溢出。

## 4. `repr(align)`、`repr(C)`、`repr(transparent)` 的作用

**类型布局**涉及大小、对齐、字段偏移和在适用情况下的 ABI。**类型布局不是内存分配策略。**

### 4.1 `#[repr(align(N))]`

```rust
#[repr(align(16))]
struct Aligned([u8; 13]);
```

提高结构体的对齐要求至至少 `N`（`N` 必须是有效的 2 的幂）。结构体大小可能包含尾部填充，例如这里通常为 16 字节。

- 对象放在栈上：编译器必须遵守对齐。
- 对象放在静态存储区：链接器/编译器必须遵守对齐。
- 对象通过分配器申请：分配器必须遵守对齐。

### 4.2 `#[repr(C)]`

```rust
#[repr(C)]
struct Header {
    a: u8,
    b: u32,
}
```

按目标平台对应的 C 结构体布局规则排列字段。常见目标上：

```text
offset 0: a (1 B)
offset 1..3: padding (3 B)
offset 4..7: b (4 B)
sizeof(Header) = 8, alignof(Header) = 4
```

它常用于 FFI、二进制布局约定等场景，但**仅加 `repr(C)` 并不能让任意 Rust 字段类型自动变成 FFI 安全类型**。

正确写法是 `#[repr(C)]`，不是 `#[repr("C")]`。

### 4.3 `#[repr(transparent)]`

```rust
#[repr(transparent)]
struct UserId(u32);
```

让包装类型与其唯一的非零大小字段具有相同的布局和 ABI。也允许符合限制的额外零大小字段。

因此 `UserId` 可以保持与 `u32` 兼容的布局，但仍然是不同的 Rust 类型。

它不会：
- 自动把值放进堆；
- 自动让类型具备 `u32` 的所有 trait；
- 自动触发一份额外的动态分配。

### 4.4 三者对比

| 属性 | 核心目的 | 会指定栈/堆/静态区域吗 |
|---|---|---|
| `repr(align(N))` | 提高对齐要求 | 不会 |
| `repr(C)` | 按 C 布局规则组织字段 | 不会 |
| `repr(transparent)` | 保持单字段包装类型的布局和 ABI 兼容性 | 不会 |

Rust 默认布局（`repr(Rust)`）**不保证普通结构体字段按源码声明顺序排列**。因此之前画的 `Bump` 树状图只表示嵌套关系，不表示确切字节偏移。

## 5. `Arena`、`UnsafeCell` 和 `Sync`：谁在真正访问内存？

### 5.1 `UnsafeCell` 不是“放到堆里”的工具

```rust
struct Arena(UnsafeCell<[u8; HEAP_SIZE]>);
```

`UnsafeCell<T>` 提供内部可变性的底层机制：允许在遵守 Rust 其他内存安全规则的前提下，经共享访问路径修改内部数据。

它不意味着：
- 自动调用 `alloc()`；
- 自动获得独立的内存块；
- 自动实现线程同步；
- 可以忽略数据竞争或别名规则。

### 5.2 外层包装与存储位置

```rust
let local = Bump::new();              // 通常是局部栈存储
static GLOBAL: Bump = Bump::new();    // 静态存储期
// Box::new(Bump::new())              // 若分配器可用，可使用动态存储
```

三种情况下，`Arena`、`UnsafeCell` 和数组仍是 `Bump` 值的组成部分。

特别注意：在已经把 `Bump` 注册为全局分配器的程序中，不要把 `Box::new(Bump::new())` 当作实际初始化全局分配器的方式；这只是用来说明布局与存储位置关系的概念例子。

### 5.3 `unsafe impl Sync for Arena` 需要什么安全论证？

```rust
unsafe impl Sync for Arena {}
```

这是一项**由程序员承担责任的安全承诺**，不是让编译器自动验证线程安全。

原先注释若写成“唯一会写这块内存的是 `Bump::alloc`”，其实不准确：`alloc` 的主要工作是**返回指针并预留区间**，真正写入用户数据的通常是获得指针的调用方。

更准确的安全依据是：

1. 所有分配通过同一个 `offset` 原子状态预留区间；
2. 成功的 CAS 保证不同分配不会拿到重叠的有效区间；
3. 分配器不把同一段已分配内存重新发给其他调用方；
4. 调用方仍需遵守 `GlobalAlloc` 的契约，正确处理指针别名、生命周期及跨线程共享；
5. 分配器自身不对已交付的用户数据进行无同步读写。

**CAS 只能保证分配区间不重叠，不能代替所有用户数据的同步机制。**

## 6. Bump 分配逻辑与关键安全细节

### 6.1 为什么使用 CAS？

两个线程可能同时读取到 `offset = 100`：

```text
线程 A：希望预留 [100, 120)
线程 B：希望预留 [100, 140)
```

如果直接 `store(end)`，两个线程可能拿到重叠区间。

使用：

```rust
offset.compare_exchange_weak(
    current,
    end,
    Ordering::Relaxed,
    Ordering::Relaxed,
)
```

只有一个线程能成功地把 `current` 更新成自己的 `end`。另一个线程必须根据最新偏移重算。

`compare_exchange_weak` 允许偶发的“伪失败”，因此通常放在循环中使用。

### 6.2 为什么这里可以使用 `Ordering::Relaxed`？

这里的原子偏移主要负责**唯一预留区间**，并不承担“发布某个对象的初始化内容给其他线程”的任务。对这个用途，`Relaxed` 的原子性足以避免偏移更新丢失或重复分配。

但如果调用方想把刚写好的对象交给另一线程读取，仍须通过适当的同步机制保证可见性，不能只依赖分配器的 `Relaxed` CAS。

### 6.3 `dealloc` 为空意味着什么？

```rust
unsafe fn dealloc(&self, _ptr: *mut u8, _layout: Layout) {
    // 不回收
}
```

这是典型的 bump/arena 风格：

- `Box` 被 drop，或 `Vec` 释放缓冲区时，可能调用 `dealloc`；
- 但 `offset` 不回退，因此内存池的相应空间**不会被再次利用**；
- 运行时间越长、累计分配越多，越可能耗尽 16 KiB；
- 扩容或重新分配也可能持续消耗新空间。

此实现适合短生命周期、启动阶段或明确受控的分配场景，不是通用长期运行堆的完整替代品。

### 6.4 `used()`、`peak()`、`alloc_count()` 代表什么？

```rust
pub fn used() -> usize {
    ALLOCATOR.offset.load(Ordering::Relaxed)
}

pub fn peak() -> usize {
    ALLOCATOR.peak.load(Ordering::Relaxed)
}

pub fn alloc_count() -> usize {
    ALLOCATOR.count.load(Ordering::Relaxed)
}

pub const fn capacity() -> usize {
    HEAP_SIZE
}
```

- `used()`：当前 bump 指针已经越过的字节数，**包含对齐填充**。
- `peak()`：统计到的历史最高 bump 偏移。
- `alloc_count()`：统计到的成功分配次数。
- `capacity()`：整个内存池的字节容量。

**特别提醒**：因为这个分配器不回收也不重置，`offset` 只增不减，所以在所有更新完成、没有并发观察窗口时，`peak()` 与 `used()` 实际上相等。`peak` 在当前设计中是冗余的；若将来增加重置或回收机制，它才更有独立意义。

统计量通过独立原子操作更新，多个指标的并发读取**不是一致性快照**，可能暂时看到 `offset` 已变化而 `peak` / `count` 尚未更新。

### 6.5 分配失败和零大小请求

- 分配器放不下请求时，`GlobalAlloc::alloc()` 应返回空指针，不能在分配器内部直接 `panic!`。
- 后续如何处理分配失败，取决于上层分配接口和程序的分配失败处理策略。
- `Layout` 本身可以描述大小为 0 的布局，但 **`GlobalAlloc::alloc` 的安全契约不允许以零大小布局调用它**。对零大小请求做 `return null_mut()` 可以作为防御分支，但不代表零大小调用因此变成符合契约的行为。
- `Box` / `Vec` 对零大小类型（ZST）通常有特殊处理，不一定真正向分配器申请存储。

### 6.6 对齐计算的修正实现（保留静态 Arena 方案）

以下示例是对原设计的**关键修正版**，重点修复绝对地址对齐与溢出检查，并保留 CAS、计数和高水位逻辑：

```rust
use core::alloc::{GlobalAlloc, Layout};
use core::cell::UnsafeCell;
use core::ptr;
use core::sync::atomic::{AtomicUsize, Ordering};

const HEAP_SIZE: usize = 16 * 1024;

#[repr(align(16))]
struct Arena(UnsafeCell<[u8; HEAP_SIZE]>);

// SAFETY: Arena 仅由下方 Bump 作为分配内存池使用。
// CAS 保证成功分配的区间互不重叠；内存不被重复分配。
// 调用方仍需遵守 GlobalAlloc 与 Rust 的并发/别名规则。
unsafe impl Sync for Arena {}

struct Bump {
    arena: Arena,
    offset: AtomicUsize,
    count: AtomicUsize,
    peak: AtomicUsize,
}

impl Bump {
    const fn new() -> Self {
        Self {
            arena: Arena(UnsafeCell::new([0; HEAP_SIZE])),
            offset: AtomicUsize::new(0),
            count: AtomicUsize::new(0),
            peak: AtomicUsize::new(0),
        }
    }
}

unsafe impl GlobalAlloc for Bump {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        // GlobalAlloc 的调用契约要求 layout.size() > 0。
        // 此处仅保留防御性分支。
        if layout.size() == 0 {
            return ptr::null_mut();
        }

        let base_ptr = self.arena.0.get().cast::<u8>();
        let base_addr = base_ptr as usize;
        let align = layout.align(); // 非零、2 的幂
        let size = layout.size();
        let mut current = self.offset.load(Ordering::Relaxed);

        loop {
            // 1. 先得到当前绝对地址
            let current_addr = match base_addr.checked_add(current) {
                Some(addr) => addr,
                None => return ptr::null_mut(),
            };

            // 2. 绝对地址向上对齐，防止溢出
            let rounded = match current_addr.checked_add(align - 1) {
                Some(addr) => addr,
                None => return ptr::null_mut(),
            };
            let aligned_addr = rounded & !(align - 1);

            // 3. 再转成相对 Arena 起点的偏移量
            let start = match aligned_addr.checked_sub(base_addr) {
                Some(start) => start,
                None => return ptr::null_mut(),
            };

            // 4. 检查分配结束位置
            let end = match start.checked_add(size) {
                Some(end) if end <= HEAP_SIZE => end,
                _ => return ptr::null_mut(),
            };

            // 5. CAS 独占 [start, end)
            match self.offset.compare_exchange_weak(
                current,
                end,
                Ordering::Relaxed,
                Ordering::Relaxed,
            ) {
                Ok(_) => {
                    self.count.fetch_add(1, Ordering::Relaxed);
                    self.peak.fetch_max(end, Ordering::Relaxed);

                    // SAFETY: end <= HEAP_SIZE，区间已经独占；
                    // 使用原 base_ptr 派生指针，保留原指针来源。
                    return unsafe { base_ptr.add(start) };
                }
                Err(actual) => current = actual,
            }
        }
    }

    unsafe fn dealloc(&self, _ptr: *mut u8, _layout: Layout) {
        // Bump allocator 不复用已释放空间
    }
}

#[global_allocator]
static ALLOCATOR: Bump = Bump::new();

pub fn used() -> usize {
    ALLOCATOR.offset.load(Ordering::Relaxed)
}

pub fn peak() -> usize {
    ALLOCATOR.peak.load(Ordering::Relaxed)
}

pub fn alloc_count() -> usize {
    ALLOCATOR.count.load(Ordering::Relaxed)
}

pub const fn capacity() -> usize {
    HEAP_SIZE
}
```

**适用边界：**

- 示例假定目标支持 `AtomicUsize` 以及这里使用的 CAS 等原子操作。某些 MCU 目标不支持相应原子指令，需要改用临界区或适合该目标的同步方案。
- 示例展示核心分配器，不包含完整的裸机启动代码、panic 处理、分配失败处理或目标链接配置。
- 即使 `Arena` 只有 16 字节对齐，修正版仍会尝试满足更高的 `Layout.align()`；若对齐填充后空间不足，则返回空指针。
- `Layout` 的有效性、调用方传入指针的正确性等，仍受 `GlobalAlloc` 安全契约约束。

## 7. 移植到真实开发板：如何指定哪段 RAM 是堆？

### 7.1 先明确 MCU 的内存地图

假设一块示例 MCU 有 128 KiB SRAM：

```text
0x2002_0000  +---------------------------+  SRAM 末端
             | 栈 / 其他预留区           |
             | ...                       |
0x2000_C000  +---------------------------+
             | 16 KiB Heap               |
             | Bump 分配器管理            |
0x2000_8000  +---------------------------+
             | .data / .bss / 其他静态区  |
             | （仅示意，布局须核实）      |
0x2000_0000  +---------------------------+  SRAM 起点
```

这只是人为规划的地址示例，**不是某块具体开发板的真实内存地图**。真实项目应查看芯片手册、目标内存布局和链接脚本，确认该地址可写、未被外设或其他用途占用。

### 7.2 路线 A：继续用静态 `Arena`

```rust
#[global_allocator]
static ALLOCATOR: Bump = Bump::new();
```

这在裸机上完全可以是合理方案。链接器把这个可写静态对象安排在合适的 RAM，分配器继续使用其中的数组。

优点：简单、边界明确、初始化容易。

局限：不容易直接指定「固定物理地址」；如果要放在特定 RAM bank 或 section，需要配合链接属性与链接脚本。

### 7.3 路线 B：链接脚本预留一段 RAM，分配器直接管理

下面是 **GNU ld 风格的概念性片段**，用于说明如何独立保留 `0x2000_8000` 开始的 16 KiB 区间。它不是可以不经修改就替换完整工程链接脚本的配置：

```ld
MEMORY
{
    RAM_DATA (rwx) : ORIGIN = 0x20000000, LENGTH = 32K
    RAM_HEAP (rw)  : ORIGIN = 0x20008000, LENGTH = 16K
    RAM_REST (rwx) : ORIGIN = 0x2000C000, LENGTH = 80K
}

/* 实际工程仍需配置 .data、.bss、栈等其他段。 */
SECTIONS
{
    .heap (NOLOAD) :
    {
        . = ALIGN(16);
        __heap_start = .;
        . += 16K;
        __heap_end = .;
    } > RAM_HEAP
}
```

这里：

- `RAM_HEAP`：定义预留的 RAM 地址范围；
- `.heap (NOLOAD)`：建立无需从程序镜像加载初始化内容的区域；
- `__heap_start` / `__heap_end`：暴露区域边界给程序；
- `ALIGN(16)`：对齐区域起始位置；
- 其他段和栈必须配置到**不重叠**的区域。

在 Rust 中可以取到边界地址：

```rust
unsafe extern "C" {
    static __heap_start: u8;
    static __heap_end: u8;
}

fn heap_region() -> (*mut u8, usize) {
    // 获取链接符号的地址，不读取符号处的字节。
    let start = core::ptr::addr_of!(__heap_start) as *mut u8;
    let end = core::ptr::addr_of!(__heap_end) as usize;
    (start, end - start as usize)
}
```

**注意**：`__heap_start` / `__heap_end` 是链接器定义的**地址符号**，不是两个实际的 `u8` 数据对象；不要去读取它们的值。

之后可让 `Bump` 保存或读取 `base` 和 `capacity`，使用同样的绝对地址对齐、CAS 和边界检查逻辑来分配。此时**不一定还需要 `Arena(UnsafeCell<[u8; N]>)` 这个包装类型**。

### 7.4 链接脚本、启动代码、分配器分别负责什么？

| 层次 | 职责 |
|---|---|
| 芯片硬件 | 提供实际 SRAM 等存储资源 |
| 链接脚本 | 安排静态数据、堆预留区、栈等区域的地址 |
| 启动代码 | 设置栈、初始化 `.data`、清零适用的 `.bss` 等 |
| `GlobalAlloc` 实现 | 在约定的内存区域中按大小和对齐分配 |
| `Box` / `Vec` 等调用方 | 申请、使用并在适当时机释放动态对象 |

### 7.5 几个真实工程中的注意事项

1. **栈与堆不能重叠。** 如果堆和栈使用同一 RAM，必须通过链接布局、固定容量和必要的运行期检查避免碰撞；仅有 Bump 的 `end <= HEAP_SIZE` 不会检查栈位置。
2. **多 RAM bank 不一定等价。** 某些 MCU 的 SRAM、DTCM、DMA 可访问区域等有不同约束，必须依据芯片手册选址。
3. **`NOLOAD` 不意味着内存一定是零。** 链接脚本保留的原始 heap 可能未初始化；而原来的 `[0; N]` 静态对象要求程序建立零初值。`GlobalAlloc` 返回的内存通常也不应被调用方假定为已清零。
4. **`.bss` 不是“堆”的同义词。** 静态 `Arena` 常可能位于 `.bss`，但它仍可以被分配器当作堆池使用。
5. **不要直接假定固定地址有效。** 必须确保它确实位于可用 RAM 内，且没有被链接器、启动代码、栈或外设占用。


### 7.6 `no_std` 中使用 `Box` / `Vec` 还需要什么？

`no_std` 不等于不能使用动态分配。只要目标平台和程序提供可用的分配器，就可以在适用的环境中引入 `alloc` crate：

```rust
#![no_std]

extern crate alloc;

use alloc::boxed::Box;
use alloc::vec::Vec;
```

还要注意：

- `core` 提供 `GlobalAlloc`、`Layout`、原子类型等底层能力；
- `alloc` 提供依赖动态分配的容器和类型；
- **全局分配器必须先可用**，否则 `Box` / `Vec` 无法正常申请存储；
- 对于完整的裸机可执行程序，还需要合适的启动入口、链接脚本、panic 处理，以及与工具链/运行时相匹配的分配失败处理方式；
- 某些嵌入式运行时或框架会替你提供其中一部分，具体要查看所用目标和运行时。

此外，普通不可变 `static` 可能被放到只读区域；**可写内存池**不能仅凭「声明成 `static`」就假设任意写入合法。当前实现通过 `UnsafeCell` 表达内部可变性，并要求最终映射到可写 RAM。

## 8. `const fn`：为什么构造函数经常需要它？

### 8.1 核心定义

```rust
const fn add(a: usize, b: usize) -> usize {
    a + b
}
```

`const fn` 的含义是：**这个函数满足常量求值的限制，因此允许在编译期常量上下文中调用**。

它不是说每次调用都必定发生在编译期。

```rust
const ANSWER: usize = add(1, 2); // 需要常量求值

fn example(x: usize) -> usize {
    add(x, 2) // 普通运行期调用也允许
}
```

### 8.2 为什么 `Bump::new()` 要写成 `const fn`？

```rust
impl Bump {
    const fn new() -> Self {
        Self {
            arena: Arena(UnsafeCell::new([0; HEAP_SIZE])),
            offset: AtomicUsize::new(0),
            count: AtomicUsize::new(0),
            peak: AtomicUsize::new(0),
        }
    }
}

#[global_allocator]
static ALLOCATOR: Bump = Bump::new();
```

`static` 的初始化表达式必须可以在常量求值上下文中求值，所以这里的 `Bump::new()` 需要是 `const fn`。

如果改成：

```rust
impl Bump {
    fn new() -> Self {
        // ...
    }
}
```

再用于：

```rust
static ALLOCATOR: Bump = Bump::new();
```

就会因为在静态初始化中调用非 `const fn` 而编译失败（典型诊断为 E0015）。

但若仅写：

```rust
fn main() {
    let local = Bump::new();
}
```

那么普通 `fn new()` 就可以使用；是否需要 `const fn` 取决于**调用上下文**。

### 8.3 为什么标准库里很多 `new()` 都是 `const fn`？

例如：

这是合法的静态初始化：

```rust
use core::sync::atomic::AtomicUsize;

static COUNTER: AtomicUsize = AtomicUsize::new(0);
```

但下面是一个**故意不能编译的反例**：

```rust,compile_fail
use core::cell::UnsafeCell;

static CELL: UnsafeCell<u32> = UnsafeCell::new(0);
// 错误：UnsafeCell<u32> 不是 Sync，不能直接作为共享 static。
```

这个反例展示了一个**独立于 const 求值的限制**：即使 `UnsafeCell::new()` 是 `const fn`，共享的 `static` 类型仍需要满足 `Sync` 约束。原来的 `Arena` 正是通过手工的 `unsafe impl Sync`，在承担安全责任的前提下解决了这一点。

标准库把简单构造函数声明为 `const fn`，是为了让它们既能用于局部变量，又能用于 `const` / `static` 等场景。

### 8.4 `const fn` 有哪些限制？

常量求值上下文中不能任意执行运行期操作。例如：

```rust
fn runtime_value() -> usize {
    10
}

const fn build() -> usize {
    runtime_value() // 错误：不能在 const fn 中调用普通 fn
}
```

还不能随意进行运行期 I/O 或通过普通堆分配器动态申请内存。允许的操作集合会随 Rust 语言版本演进，具体以所用工具链的规则为准。

但 `const fn` **不是完全不能有局部可变变量、分支或循环**；许多纯计算可以在常量求值时完成。

### 8.5 `const`、`static`、`const fn` 的区别

```rust
struct Config {
    size: usize,
}

impl Config {
    const fn new(size: usize) -> Self {
        Self { size }
    }
}

const CONFIG: Config = Config::new(1024);
static GLOBAL_CONFIG: Config = Config::new(2048);

fn example() {
    let local = Config::new(4096);
}
```

| 写法 | 解决的问题 |
|---|---|
| `const CONFIG` | 定义可用于常量求值的常量值，不承诺独立固定存储地址 |
| `static GLOBAL_CONFIG` | 定义具有静态存储期的对象 |
| `const fn new()` | 允许构造函数参与编译期常量求值 |

**编译期构造 ≠ 放在 ROM。** 对于需要在运行时修改的全局分配器，最终仍需要可写的存储空间。常见裸机程序可能通过 `.bss` 和启动代码建立全零初始状态；具体由目标和链接配置决定。

### 8.6 为什么 `Bump::new()` 的整个函数可以是 `const fn`？

因为其内部操作都适用于常量求值：

- `[0; HEAP_SIZE]`：编译期可构造的数组；
- `UnsafeCell::new(...)`：支持常量求值；
- `AtomicUsize::new(0)`：支持常量求值；
- `Arena(...)` / `Bump { ... }`：可在常量求值中构造值。

**一句话：`const fn` 解决“能否在编译期构造”，`static` 解决“对象存储期”，`GlobalAlloc` 解决“如何在运行期动态分配”。**

## 9. 将所有概念串成一条完整链路

```text
[编写类型]
  Arena(UnsafeCell<[u8; N]>)
          |
          | repr(align(16))：要求 Arena 的存储地址至少 16B 对齐
          v
[定义构造函数]
  const fn Bump::new()
          |
          | 常量求值：构造初始状态
          v
[定义静态对象]
  static ALLOCATOR: Bump = Bump::new()
          |
          | 链接器/启动代码安排可写静态存储
          v
[注册分配器]
  #[global_allocator]
          |
          | Box / Vec 等需要分配时调用
          v
[运行期分配]
  GlobalAlloc::alloc(Layout)
          |
          | 绝对地址对齐 + 容量检查 + CAS
          v
[返回指针]
  指向静态 Arena 内部的一个互不重叠的区间
          |
          | 调用方负责对象初始化与正确使用
          v
[释放]
  dealloc() 不回收 -> offset 不回退
```

如果改用链接器预留的专用 RAM 区域，变化主要发生在**后备内存来源**：

```text
原方案：static Bump -> 内嵌 Arena 数组 -> alloc()
新方案：链接脚本预留 RAM -> 起止地址符号 -> Bump -> alloc()
```

分配算法的基本思想不变。

## 10. 常见误区与精确修正

| 容易产生的理解 | 更准确的说法 |
|---|---|
| `Arena` 是数组，所以一定在栈上 | 数组类型不决定存储位置；当前它嵌在静态 `ALLOCATOR` 中 |
| 加了 `#[global_allocator]`，`Arena` 就被搬进堆 | 该属性只是注册分配器，不负责移动内存 |
| 静态数组做的分配器不算真正的堆 | 它是以静态 RAM 为后备存储的动态分配器 |
| 只有堆上的数据才需要对齐 | 栈、静态存储和动态分配都要满足类型对齐 |
| 先分配 13B，余下 3B 一定废弃 | 是否跳过取决于下一次请求的对齐 |
| `repr(align(16))` 能满足所有 `Layout` | 只能保证至少 16B；更高对齐必须另行处理 |
| 对齐 `offset` 就等于对齐指针 | 只有基地址满足请求对齐时才成立 |
| `repr(C)`、`repr(transparent)` 决定存储区域 | 它们约束布局/ABI，不决定栈或堆 |
| `UnsafeCell` 保证并发安全 | 它只提供内部可变性的底层机制；并发安全需另外论证 |
| `Bump::alloc` 是唯一会写 Arena 的函数 | 分配器返回区间后，调用方通常会写入这些字节 |
| `Relaxed` CAS 可以同步所有用户数据 | 它只满足这里的区间预留需要；对象跨线程发布仍需同步 |
| `const fn` 每次调用都在编译期执行 | 它只是允许常量求值；普通调用也可在运行期执行 |
| `const fn` 让对象位于 ROM | 初始化时间与存储位置是不同问题 |
| `dealloc` 被调用就会回收内存 | 此实现的空 `dealloc` 不回收任何区间 |
| `.heap (NOLOAD)` 的内存一定全零 | `NOLOAD` 不承诺清零，需看启动代码和内存初始化方案 |
| `used()` 表示所有存活对象大小之和 | 它表示 bump 指针消耗的空间，包含 padding 和不再使用的旧分配 |

## 11. 继续学习时最值得做的 5 个练习

1. **验证布局**：分别打印或检查 `size_of::<Arena>()`、`align_of::<Arena>()`、`size_of::<Bump>()`、`align_of::<Bump>()`，并理解为何不能假定 `Bump` 的字段顺序。
2. **验证对齐**：用 `Layout::from_size_align(13, 1)`、`(8, 8)`、`(8, 32)` 依次分配，检查返回指针的地址是否满足 `addr % align == 0`。
3. **验证填充**：比较 `used()` 的增长与实际请求大小之和，观察 padding。
4. **验证失败与回收行为**：不断分配直到返回空指针，再调用 `dealloc()`，观察 `used()` 不会下降。
5. **移植到开发板**：先查看 `memory.x` 或链接脚本，找出 `.data`、`.bss`、栈顶、可用 RAM 区间，再尝试专用 `.heap` 段。务必确认区域互不重叠。

**延伸问题**：如果堆向高地址增长、栈向低地址增长，而二者共用同一块 RAM，那么谁来保证不会碰撞？答案涉及链接脚本的边界规划、启动时的栈设置、固定容量以及运行期的栈使用分析/保护机制。

## 13. 最终知识框架

以后分析任何 Rust 内存相关代码，都可以依次问：

1. **类型是什么？** `struct`、数组、包装类型，各自有哪些字段？
2. **布局是什么？** `size_of`、`align_of`、字段偏移、`repr` 约束？
3. **对象在哪里？** 局部变量、`static`，还是由分配器返回的动态区域？
4. **初始化在什么时候？** 常量求值、启动阶段，还是运行期？
5. **谁管理内存？** 编译器、链接器、启动代码、全局分配器，还是调用方？
6. **对齐是否满足？** 检查**最终实际地址**，而不仅是偏移量。
7. **并发安全如何保证？** 谁拥有区间、谁可以读写、何时同步？
8. **失败与释放怎么办？** 空指针、容量耗尽、是否回收、是否可能泄漏？
9. **硬件上是否可行？** RAM 地址、容量、访问权限、原子指令、栈与其他段是否冲突？

> **一句话总结**：你写的 Bump allocator 使用具有静态存储期的数组作为后备内存，通过原子偏移管理动态分配；`repr` 决定布局与对齐要求，`const fn` 支持静态初始化，而链接脚本可以在真实 MCU 上进一步决定分配器管理哪一段 RAM。这几个概念彼此关联，却绝不能混为一谈。
