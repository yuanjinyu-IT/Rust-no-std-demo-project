> 要真正理解 Rust 的 `main()` 为什么会涉及 `libc`、`__libc_start_main`，就需要理解操作系统如何创建进程、加载可执行文件，以及如何把控制权交给用户程序。

不过这里有一个非常重要的区分：

**操作系统启动（Boot）和用户程序启动（Process Startup）是两个不同的过程。**

它们确实存在联系，但我们不需要每次研究 `main()` 都从 Bootloader 开始。

我按照从浅到深的顺序，把这些概念串起来。

# 一、什么是三元组（Target Triple）？

你看到的：

```text
x86_64-unknown-linux-gnu
```

是 Rust 的一个**目标平台标识（Target Triple）**。

它告诉 Rust 编译器：

> 我要把这份 Rust 代码编译成能够在哪种计算机、哪种操作系统环境下运行的程序？

虽然叫 Triple（三元组），但实际上经常包含四个部分。

我们拆开看：

```text
x86_64 - unknown - linux - gnu
   │       │        │      │
   │       │        │      └── ABI / 运行时环境
   │       │        └───────── 操作系统
   │       └────────────────── 厂商
   └────────────────────────── CPU 架构
```

## 1. x86_64：CPU 架构

它表示目标机器采用 x86-64 指令集。

你写：

```rust
fn main() {
    println!("Hello, world!");
}
```

CPU 实际上不认识 Rust。

它只认识机器指令。

因此，编译器需要把 Rust 转换成特定 CPU 能执行的指令。

例如：

```asm
mov rax, 60
xor rdi, rdi
syscall
```

这是一段 x86-64 Linux 上通过系统调用退出进程的汇编代码。

如果换成 ARM64：

```text
aarch64-unknown-linux-gnu
```

编译器就需要生成 ARM64 指令，而不是 x86-64 指令。

所以：

**CPU 架构决定编译器最终生成什么机器指令。**

---

## 2. unknown：厂商

这个字段表示 Vendor（厂商）。

常见的有：

```text
unknown
apple
pc
```

例如：

```text
x86_64-apple-darwin
x86_64-pc-windows-msvc
x86_64-unknown-linux-gnu
```

`unknown` 并不是说编译器不知道你的 CPU 厂商是谁。

而是说这个目标平台没有指定特定厂商。

对理解程序启动来说，这个字段暂时不重要。

---

## 3. linux：操作系统

这一部分开始涉及你关心的 OS 知识。

为什么编译器需要知道操作系统？

因为：

**不同操作系统提供给用户程序的运行接口并不相同。**

例如，你希望程序向终端输出：

```rust
println!("Hello");
```

最终就需要操作系统提供某种机制，将数据写入标准输出。

在 Linux 上，底层可以使用：

```text
write 系统调用
```

在 Windows 上，则有另一套系统 API。

另外，不同操作系统在以下方面也可能不同：

- 可执行文件格式
- 系统调用接口
- 进程启动约定
- 动态链接机制
- 线程与异常处理机制

例如：

| 操作系统 | 常见可执行文件格式 |
|---|---|
| Linux | ELF |
| Windows | PE |
| macOS | Mach-O |

因此：

```text
x86_64-unknown-linux-gnu
```

意味着编译器要生成符合 Linux 平台要求的程序。

但这里有一个问题：

**仅仅知道是 Linux，还不够。**

因为 Linux 上可能存在不同的用户态运行时环境。

这就引出了最后一个字段。

---

# 二、gnu 是什么？

这是你问题中非常关键的一部分。

首先：

**GNU 不是 Linux，Linux 也不是 GNU。**

它们是两个不同的项目。

## 1. Linux 严格来说是内核

我们平时说：

```text
我使用 Linux 操作系统
```

但从严格的技术概念来说：

Linux 主要指的是 Linux Kernel（Linux 内核）。

内核负责：

```text
进程管理
内存管理
文件系统
设备驱动
网络协议栈
系统调用
```

例如：

当一个程序需要读取文件：

```rust
let content = std::fs::read_to_string("hello.txt")?;
```

最终会通过操作系统提供的接口，请求内核执行相关操作。

但问题是：

**只有 Linux 内核，并不等于拥有一个完整的常规用户态运行环境。**

我们还需要很多用户态组件。

例如：

- Shell
- 系统工具
- C 标准库
- 动态链接器
- 其他基础运行库

GNU 项目提供了其中很多重要组件。

## 2. GNU 是一个自由软件项目

GNU 是：

**GNU's Not Unix**

这是一个递归缩写。

GNU 项目最初的目标是开发一套自由的、类 Unix 的操作系统。

它开发了很多重要的软件：

```text
GCC
GDB
Bash
glibc
Coreutils
```

其中与你当前问题关系最大的就是：

**glibc（GNU C Library）**。

注意这几个概念的区别：

```text
GNU
 └── GNU 项目
      └── glibc
           └── GNU C 标准库实现
```

glibc 是一个具体的软件库。

而 `libc` 通常泛指 C 标准库及其相关系统接口实现。

glibc 是 Linux 上常见的 libc 实现之一。

另外还有：

```text
musl libc
```

这就解释了为什么 Rust 会有两个不同的目标：

```text
x86_64-unknown-linux-gnu

x86_64-unknown-linux-musl
```

它们都是：

- x86-64 CPU
- Linux 操作系统

但它们使用的 C 库环境不同。

| Target | C 库环境 |
|---|---|
| `x86_64-unknown-linux-gnu` | glibc |
| `x86_64-unknown-linux-musl` | musl |

这里的 `gnu` 并不是说 Rust 代码要编译成 C，也不是说必须使用 GCC。

它主要标识目标平台采用 GNU/glibc 相关的 ABI 和运行时约定。

---

# 三、为什么 Rust 要用 libc？它不是 Rust 语言吗？

这是整件事情最有意思的地方。

你可能会想：

> Rust 明明是一门独立的编程语言，为什么程序启动还要经过 C 标准库？

原因是：

**编程语言与程序运行环境是两个不同的层次。**

我们先看一个例子。

```rust
fn main() {
    println!("Hello, Rust!");
}
```

你可能以为程序运行的过程是：

```text
Linux 内核
    ↓
Rust main()
    ↓
println!()
    ↓
程序退出
```

但在常见的 glibc Linux 环境中，实际情况更接近：

```text
Linux 内核
    │
    │ execve()
    ▼
加载 ELF 可执行文件
    │
    ▼
动态链接器（如果需要）
    │
    ▼
程序入口 _start
    │
    ▼
glibc 的 __libc_start_main
    │
    ▼
Rust 运行时启动代码
    │
    ▼
Rust main()
    │
    ▼
Termination::report()
    │
    ▼
进程退出
```

这里有个容易混淆的地方：

**`_start`、`__libc_start_main` 和 Rust 的 `main` 不是同一个东西。**

它们属于不同层次。

我们分别看。

## 1. Linux 内核不知道什么是 Rust main()

这是一个非常重要的事实。

Linux 内核并不关心你的程序是用什么语言编写的。

可以是：

```text
C
C++
Rust
Go
Zig
Assembly
```

内核主要关心：

> 这个可执行文件是什么格式？应该映射哪些内容到内存？程序入口地址在哪里？

对于 ELF 文件，其中有一个重要字段：

```text
e_entry
```

它描述 ELF 的入口虚拟地址。

内核和动态链接器按照 ELF 的加载约定完成准备后，控制权才会到达程序的入口代码。

内核并不会主动去寻找：

```rust
fn main()
```

因为 `main` 是编程语言和运行时层面的约定，而不是 Linux 内核要求的函数名称。

---

## 2. 那么 `_start` 是什么？

`_start` 通常是用户程序的底层入口符号。

在常见的 glibc 程序中，它由 C 运行时启动代码提供。

例如：

```text
glibc
 └── crt1.o
      └── _start
```

这里的 `crt` 可以理解为 C Runtime 的启动代码。

程序刚进入 `_start` 时，还不能简单地把它当作普通的 Rust 函数调用环境。

它需要遵循操作系统和平台 ABI 的启动约定。

例如，启动环境中包含：

```text
argc
argv
envp
auxv
```

分别与以下信息有关：

```text
argc  → 命令行参数数量
argv  → 命令行参数
envp  → 环境变量
auxv  → 辅助向量
```

在 Linux x86-64 上，进程初始栈中就包含这些信息。

`_start` 会根据平台约定处理这些数据，并把控制权交给后续运行时初始化代码。

在典型的 glibc 程序中，就会涉及：

```c
__libc_start_main(...)
```

这个函数负责协调 C 运行时初始化、调用用户程序入口函数，以及处理返回后的退出流程等工作。

需要注意，具体启动细节依赖 glibc 版本、链接方式和 Rust 目标平台实现。

---

## 3. Rust 为什么不自己实现所有启动代码？

其实可以。

**Rust 并不是必须依赖 libc 才能运行。**

Rust 选择是否使用 libc，取决于目标平台、标准库支持和链接配置。

例如：

在普通的 Linux GNU 环境中，Rust 可以复用 glibc 提供的启动基础设施。

这有很多好处：

- 遵循成熟的 Linux 用户态 ABI
- 复用现有动态链接和启动机制
- 与 C/C++ 生态兼容
- 减少重复实现平台相关基础设施

但是 Rust 也可以不依赖 glibc。

例如，编写一个不使用标准库的 Linux 程序：

```rust
#![no_std]
#![no_main]
```

然后自行提供程序入口。

理论上可以直接通过 Linux 系统调用完成输出、退出等操作。

不过这样一来，很多原本由标准库或运行时处理的事情，就需要自己负责。

例如：

```text
程序入口
系统调用
panic 处理
内存分配
线程支持
```

这也是为什么 Rust 在嵌入式、操作系统内核等领域经常使用：

```rust
#![no_std]
```

因为这些环境可能根本没有 libc。

所以你可以这样理解：

> Rust 是编程语言；libc 是某些目标平台提供的用户态运行时基础设施。Rust 可以使用它，但 Rust 语言本身并不依赖它存在。

---

# 四、真正重要的区别：libc 和 Linux 内核是什么关系？

这里需要建立一个非常清晰的分层模型。

```text
┌────────────────────────────────────┐
│            Rust 程序               │
│                                    │
│ fn main() {                        │
│     println!("Hello");             │
│ }                                  │
└────────────────────────────────────┘
                  │
                  ▼
┌────────────────────────────────────┐
│        Rust 标准库 std             │
│                                    │
│ std::io                            │
│ std::fs                            │
│ std::thread                        │
└────────────────────────────────────┘
                  │
                  ▼
┌────────────────────────────────────┐
│      用户态系统接口 / libc         │
│                                    │
│ glibc / musl / 其他实现            │
└────────────────────────────────────┘
                  │
                  ▼
══════════════ 用户态 / 内核态 ══════════════
                  │
                  ▼
┌────────────────────────────────────┐
│           Linux Kernel             │
│                                    │
│ 进程管理                           │
│ 虚拟内存                           │
│ 文件系统                           │
│ 系统调用                           │
└────────────────────────────────────┘
                  │
                  ▼
┌────────────────────────────────────┐
│              硬件                  │
│                                    │
│ CPU / RAM / SSD / 网卡             │
└────────────────────────────────────┘
```

不过这张图是概念上的简化。

**Rust 标准库并不是所有操作都必须经过 libc。**

在 Linux 上，某些操作会通过 libc 提供的接口完成，某些操作也可以直接使用系统调用。

因此不能简单认为：

```text
Rust → libc → Linux
```

是所有代码都必须遵循的固定调用链。

另外：

**libc 运行在用户态，不属于 Linux 内核。**

它只是帮助用户程序使用系统服务的一种基础库。

这意味着你需要区分两个概念：

### 函数调用

例如：

```c
printf("hello");
```

这是用户态函数调用。

### 系统调用

例如 Linux 的：

```text
write
```

这是用户程序请求内核服务的机制。

两者不是一回事。

`printf()` 可以在用户态完成格式化和缓冲，必要时再通过系统调用输出数据。

---

# 五、从 Bootloader 到 Rust main()，完整流程是什么？

现在我们可以回答你最开始的直觉：

> 是不是应该从 Bootloader 启动 OS 内核，再到 OS 内核启动进程，最后到 Rust main？

是的。

如果你希望理解一个程序从计算机开机到执行的完整过程，可以把它分成两个阶段。

## 第一阶段：操作系统启动

以常见的 x86-64 UEFI Linux 系统为例：

```text
计算机通电
    │
    ▼
CPU 开始执行固件代码
    │
    ▼
UEFI 固件初始化硬件
    │
    ▼
启动 Bootloader
    │
    ▼
Bootloader 加载 Linux 内核
    │
    ▼
Linux Kernel 开始运行
    │
    ├── 初始化内存管理
    │
    ├── 初始化中断机制
    │
    ├── 初始化设备驱动
    │
    ├── 初始化进程调度
    │
    └── 初始化文件系统
    │
    ▼
启动第一个用户态进程
    │
    ▼
init / systemd
    │
    ▼
启动其他系统服务
    │
    ▼
系统进入正常运行状态
```

这里需要注意：

Bootloader 并不负责启动你写的 Rust 程序。

它的主要任务是帮助启动操作系统。

而且不是所有系统都一定经过独立的 Bootloader，例如 UEFI 也可以通过其他方式直接引导 Linux 内核。

---

## 第二阶段：用户程序启动

假设你已经打开终端，执行：

```bash
cargo run
```

为了简化，我们先假设 Rust 程序已经编译完成。

实际过程可以分成两部分：

```text
Shell
    │
    │ 启动可执行文件
    ▼
创建子进程
    │
    ▼
execve()
    │
    ▼
Linux 内核
    │
    ├── 识别 ELF 文件
    │
    ├── 建立新的进程地址空间映像
    │
    ├── 映射程序代码和数据
    │
    ├── 设置用户栈
    │
    ├── 准备 argc / argv / envp / auxv
    │
    └── 设置初始执行上下文
    │
    ▼
动态链接器（动态链接程序）
    │
    ├── 加载所需共享库
    │
    ├── 处理必要的重定位
    │
    └── 转交控制权
    │
    ▼
_start
    │
    ▼
__libc_start_main
    │
    ▼
Rust 运行时启动代码
    │
    ▼
fn main()
    │
    ▼
程序退出
```

这里再纠正一个常见误解：

**`execve()` 本身并不创建新进程。**

通常是 Shell 先通过 `fork()` 或相关机制创建子进程，然后子进程调用 `execve()`，用新程序替换当前进程映像。

所以：

```text
fork  → 创建进程
execve → 替换进程映像
```

这是两个不同的操作。

当然，实际的进程创建方式还可能涉及 `clone()`、`posix_spawn()` 等机制。

---

# 六、为什么 main() 不是程序真正的入口？

现在我们回到你最初看到的 Rust 代码。

```rust
fn main() {
    println!("Hello");
}
```

你可能会认为：

```text
main 是程序的入口
```

这句话在 Rust 语言层面是正确的。

但从 ELF 和操作系统的角度看，就不够准确。

我们需要区分三个层次：

| 层次 | 入口 |
|---|---|
| ELF 可执行文件 | ELF Header 中的 `e_entry` |
| 用户态启动代码 | 通常是 `_start` |
| Rust 应用程序 | `fn main()` |

它们之间大致是：

```text
ELF entry
    ↓
_start
    ↓
运行时初始化
    ↓
Rust main
```

因此：

**`main()` 是 Rust 应用逻辑的入口，而不一定是可执行文件最初执行的机器指令。**

这也是为什么 Rust 的 `main()` 可以写成：

```rust
fn main() {
    println!("Hello");
}
```

却不需要自己处理：

```text
进程初始栈
ELF 加载
动态链接
运行时初始化
进程退出
```

因为这些事情由操作系统、链接器以及运行时启动代码共同完成了。

---

# 七、我们甚至可以自己验证

如果你正在使用 x86-64 Linux，可以做一个非常有意思的实验。

先创建 Rust 项目：

```bash
cargo new hello
cd hello
cargo build
```

查看目标平台：

```bash
rustc -vV
```

你可能看到：

```text
host: x86_64-unknown-linux-gnu
```

然后查看可执行文件：

```bash
file target/debug/hello
```

通常可以看到它是 ELF 文件。

接着执行：

```bash
readelf -h target/debug/hello
```

关注：

```text
Entry point address:
```

这个地址就是 ELF Header 中的入口地址。

注意：

它通常不是 Rust `main()` 的地址。

继续执行：

```bash
readelf -l target/debug/hello
```

如果程序是动态链接的，你可能看到：

```text
INTERP
```

以及动态链接器路径。

接着：

```bash
readelf -Ws target/debug/hello | grep __libc_start_main
```

在典型的动态链接 glibc 程序中，你可能看到对 `__libc_start_main` 的符号引用。

最后：

```bash
objdump -d target/debug/hello
```

找到 `_start` 附近的汇编代码。

在常见的 glibc x86-64 启动实现中，你可以观察到它如何调用 `__libc_start_main`。

这个实验能够让你把：

```text
Rust 源代码
    ↓
编译器
    ↓
ELF
    ↓
_start
    ↓
glibc
    ↓
Rust main
```

真正联系起来。

具体符号、地址和汇编指令会受到编译器版本、链接方式以及发行版配置影响。

# 八、最后，我建议你建立一个更完整的知识框架

你现在的问题，其实跨越了计算机系统的四个重要领域。

| 领域 | 你需要理解什么 | 对应你的问题 |
|---|---|---|
| 计算机体系结构 | CPU、指令集、特权级、内存 | 为什么有 x86_64？ |
| 操作系统 | 进程、虚拟内存、系统调用、ELF 加载 | OS 如何启动程序？ |
| 编译与链接 | 目标文件、符号、链接器、ABI | Rust 如何变成可执行文件？ |
| 语言运行时 | `_start`、libc、Rust std、main | 为什么 main 之前还有代码？ |

我特别建议你注意一个概念：

## ABI（Application Binary Interface）

**你现在看到的这些问题，最终都会汇聚到 ABI。**

比如：

为什么：

```text
x86_64-unknown-linux-gnu
```

与：

```text
x86_64-unknown-linux-musl
```

不完全相同？

为什么 Rust 能调用 C 函数？

为什么 `_start` 能调用 `__libc_start_main`？

为什么程序启动时参数放在特定位置？

为什么不同操作系统不能直接运行彼此的可执行文件？

这些都与 ABI、可执行文件格式以及操作系统接口有关。

ABI 规定了二进制组件如何协作，包括调用约定、数据布局、符号链接规则等；而进程启动还有 ELF、操作系统和运行时共同定义的约定。

所以，你可以把这条知识链理解为：

```text
Rust 源代码
      │
      ▼
编译器
      │
      ▼
机器指令 + ABI
      │
      ▼
链接器
      │
      ▼
ELF 可执行文件
      │
      ▼
Linux execve
      │
      ▼
动态链接器 / 启动代码
      │
      ▼
Rust main()
      │
      ▼
系统调用
      │
      ▼
Linux Kernel
      │
      ▼
硬件
```

## 九、一个特别值得深入思考的问题

你现在已经知道：

```rust
fn main() {
    println!("Hello");
}
```

背后涉及 Rust 标准库、libc、ELF 和 Linux。

但接下来有一个更根本的问题：

**假设我们完全不用 Rust 标准库，也不用 libc，只用汇编和 Linux 系统调用，能不能写出一个可以运行的程序？**

答案是：**可以。**

而且这个程序可以非常简单：

```asm
.global _start

.section .text
_start:
    mov $60, %rax
    xor %rdi, %rdi
    syscall
```

这是 Linux x86-64 下的 GNU 汇编器 AT&T 语法。

它做的事情只有：

```text
_start
   │
   ▼
rax = 60       # exit 系统调用号
   │
   ▼
rdi = 0        # 退出状态
   │
   ▼
syscall        # 进入 Linux 内核
   │
   ▼
进程退出
```

这里：

- 没有 Rust
- 没有 C
- 没有 libc
- 没有 `main()`
- 没有 `__libc_start_main`

但它仍然是一个能够正常运行的 Linux 程序。

这说明一个非常重要的事实：

> **操作系统不要求程序必须使用某种编程语言，也不要求必须存在 `main()`。操作系统要求的是程序符合它支持的可执行文件格式、加载约定和执行环境。**

### 我建议你的下一步

与其马上从 Bootloader 开始研究整个 Linux 启动过程，我更推荐你先沿着下面这条路线深入：

**① Rust 源代码如何编译成 ELF → ② ELF 的入口 `_start` 是什么 → ③ Linux 的 `execve()` 如何加载 ELF → ④ CPU 如何从用户态通过 `syscall` 进入内核 → ⑤ libc 和 Rust std 在其中分别扮演什么角色。**

等这条路线理解透彻，再反过来研究 Bootloader 如何启动 Linux 内核，你会更容易把整个计算机系统串起来。

**尤其值得先研究的是：当你在 Shell 中输入 `./hello` 并按下回车时，从那一刻开始，CPU、Shell、Linux 内核、ELF 加载器和 Rust 运行时究竟各自做了什么？**

把这个过程研究清楚，你对 Rust `main()` 的理解就会从语言语法深入到计算机系统的运行机制。
