# Rust 裸机启动：Cortex-M、x86-64 与函数调用边界

本文围绕一个问题展开：**在没有常规操作系统运行环境的情况下，CPU 如何进入 Rust 程序？** 重点区分 CPU 架构、启动运行时、函数序言与尾声，以及 `asm!` 和 `naked_asm!` 的边界。

## 1. Cortex-M 与 x86-64 是什么关系？

**它们不完全处于同一抽象层。** x86-64 是指令集架构（ISA）；Cortex-M 是 ARM 面向微控制器的 CPU 内核系列，具体内核实现相应的 ARM 架构。

| 名称 | 层次 | 示例或说明 |
|---|---|---|
| x86-64 | 指令集架构 | Intel Core、AMD Ryzen 等实现它 |
| ARMv7-M / ARMv7E-M | 指令集架构 | 面向微控制器的 ARM 架构 |
| Cortex-M4 | CPU 内核 | 实现 ARMv7E-M |
| STM32F407 | 微控制器芯片（MCU） | 内含 Cortex-M4 内核 |
| STM32F4 Discovery | 开发板 | 搭载相应 MCU |

所以 Cortex-M 常用于嵌入式开发板，但它既不是开发板本身，也不是某个单独的 ISA 名称。

`cortex-m-rt` 中的 `rt` 指 *runtime*（运行时）：这是负责 Cortex-M 裸机程序启动支持的 Rust crate，并非 CPU 架构。

## 2. `kernel_main()` 究竟做了什么？

```rust
use cortex_m_rt::entry;

#[entry]
fn kernel_main() -> ! {
    loop {
        core::hint::spin_loop();
    }
}
```

这个函数本身**没有执行具体业务逻辑**，只是不断自旋，永不正常返回。但它在启动链路中的位置很重要：

```text
CPU Reset
   │
   ├─ 硬件从向量表读取初始 MSP 和 Reset Handler 地址
   ▼
Reset Handler（由 cortex-m-rt 提供）
   │
   ├─ 清零 .bss
   ├─ 初始化 .data（按镜像布局需要从非易失存储器复制到 RAM）
   └─ 完成其他必要的启动准备
   ▼
kernel_main()
   │
   ▼
loop { core::hint::spin_loop(); }
```

- `kernel_main` **不是特殊的 Rust 函数名**。`#[entry]` 属性过程宏才是关键：它检查入口函数的签名，生成启动代码所需的入口符号（通常为 `main`），使 Reset Handler 能够调用它。
- `-> !` 中的 `!` 是 Rust 的 *never type*，表示函数不会正常返回。
- `core::hint::spin_loop()` 是自旋等待提示，可能映射为相应架构的提示指令，例如 x86 上的 `PAUSE`。它不是睡眠，也不保证省电。

## 3. 什么是函数序言与函数尾声？

**函数序言（function prologue）**是函数刚进入时为建立执行环境而运行的指令；**函数尾声（function epilogue）**是在函数返回前恢复执行环境的指令。

它们不是源代码层面必须出现的固定模板，而是编译器根据 **ABI、优化、寄存器使用、局部变量和栈帧需求**生成的机器指令。一个函数也可以完全没有传统意义上的序言或尾声。

### 3.1 栈帧与调用约定

在常见的 x86-64 调用模型中：

- `rsp` 是栈指针，指向当前栈顶附近的位置。
- `rbp` 可以作为栈帧指针，但优化后的函数经常省略它。
- `call` 通常会把返回地址压入栈，然后跳转到被调用函数。
- `ret` 从栈中取出返回地址并跳转回调用者。
- ABI 规定参数、返回值、栈对齐和哪些寄存器必须由被调用者保存。

以 **System V AMD64 ABI**（常见于 Linux x86-64）为例，调用者在执行 `call` 之前通常要让 `rsp` 按 16 字节对齐。由于 `call` 压入一个 8 字节返回地址，普通被调用函数刚进入时通常满足：

```text
(rsp + 8) % 16 == 0
```

Windows x64 有不同的 ABI 细节（例如 shadow space）；因此不能把一个平台上的规则无条件套到所有 x86-64 程序。

### 3.2 一个典型的函数序言

下面是教学用途的 x86-64 示例，展示一种传统的、保留帧指针的栈帧：

```asm
push rbp          ; 保存调用者的 rbp；rsp -= 8
mov  rbp, rsp     ; 将当前栈顶作为本函数的帧基址
sub  rsp, 32      ; 为局部数据预留 32 字节
```

假设这是通过正常的 `call` 进入的函数，其栈布局可简化为：

```text
较高地址
┌─────────────────────────────┐
│ 调用者的栈内容              │
├─────────────────────────────┤
│ 返回地址                    │  [rbp + 8]
├─────────────────────────────┤
│ 旧 rbp                      │  [rbp]
├─────────────────────────────┤
│ 本函数的局部栈空间          │
│ （此例预留 32 字节）        │
└─────────────────────────────┘
较低地址                      ← rsp
```

这只是一个典型布局，不代表所有函数的局部变量一定按这种方式存放。

### 3.3 一个典型的函数尾声

对应的尾声可以是：

```asm
mov rsp, rbp      ; 丢弃本函数预留的局部栈空间
pop rbp           ; 恢复调用者的 rbp
ret               ; 读取返回地址并返回
```

其中：

```asm
leave
ret
```

在这种传统栈帧结构下，也能实现等效的栈帧拆除与返回。

如果函数还使用了 ABI 要求保留的其他寄存器，例如某些场景中的 `rbx`、`r12`，它也需要适当地保存并恢复它们。

### 3.4 为什么序言与尾声不是固定的？

编译器可以根据情况：

- 省略 `rbp` 帧指针，直接相对 `rsp` 寻址；
- 将局部变量完全放在寄存器里，不分配局部栈空间；
- 内联函数，使其根本不形成独立的调用边界；
- 将尾调用优化成跳转，避免常规 `call`/`ret` 配对；
- 为大栈帧、栈保护、异常展开等生成额外指令。

例如，一个足够简单的函数可能只有：

```asm
lea eax, [rdi + 1]
ret
```

因此，**“普通函数可能有序言”不等于“普通函数必然先执行 `push rbp`”**。真正的问题在于：如果启动时还没有有效栈，就不能依赖编译器生成的普通函数一定不会使用它。

### 3.5 为什么这会影响裸机 `_start`？

假设 CPU 刚进入你控制的启动入口时，`rsp` 尚未有效初始化。如果编译器在你的第一条 Rust 语句之前生成：

```asm
push rbp
```

那么这条指令就可能写入无效内存。

所以当你需要**在尚未建立栈的条件下执行第一段代码**时，必须选择不会偷偷引入普通函数序言的入口实现方式，例如裸函数或合适的独立汇编入口。

但这取决于启动协议：有些 bootloader 或固件已经提供可用栈，不能笼统地说所有 x86-64 裸机入口的 `rsp` 都是垃圾值。

## 4. `asm!` 与 `naked_asm!` 的区别

### 4.1 `asm!`：在普通 Rust 函数中嵌入汇编

```rust
use core::arch::asm;

fn example() {
    unsafe {
        asm!("nop");
    }
}
```

这里的 `asm!` 只是函数中的一段内联汇编。编译器仍然负责该函数的整体代码生成，包括需要时的栈帧、寄存器分配和序言/尾声。

```text
可能存在的编译器生成序言
             ↓
        asm!("nop")
             ↓
可能存在的编译器生成尾声
```

因此，在一个尚未建立栈的普通函数里用 `asm!` 修改 `rsp`，不能保证此前编译器没有访问栈，也可能破坏编译器对栈状态的假设。

### 4.2 `naked_asm!`：裸函数的汇编主体

```rust
#[unsafe(naked)]
unsafe extern "C" fn my_entry() {
    core::arch::naked_asm!(
        "nop",
        "ret",
    );
}
```

`#[unsafe(naked)]` 表示函数不使用编译器生成的常规序言和尾声；`naked_asm!` 提供裸函数的汇编主体。

| 特性 | `asm!` | `naked_asm!` |
|---|---|---|
| 使用位置 | 普通 Rust 函数内部 | 裸函数的汇编主体 |
| 常规序言/尾声 | 可能由编译器生成 | 不生成 |
| 栈帧管理 | 编译器仍可管理 | 由编写者负责 |
| 操作数 | `in`、`out`、`inout`、`const`、`sym` 等 | `const`、`sym` |
| 典型用途 | 特殊 CPU 指令、寄存器操作 | 启动入口、上下文切换入口 |

**“裸”并不是一种不同的汇编语言。** `mov`、`lea`、`jmp` 等指令并没有改变；区别在于编译器是否自动处理常规函数边界。

裸函数也不等于可以无视 ABI：若它作为普通函数被调用，就必须正确处理调用者期待的寄存器、栈和返回约定；如果它是启动入口，则应遵守相应启动协议，而不是假设它由普通 `call` 进入。

## 5. x86-64 的 `_start` 负责什么？

下面只展示**概念性结构**，不是可直接编译、链接和启动的完整实现：

```rust
#[unsafe(naked)]
#[unsafe(no_mangle)]
#[unsafe(link_section = ".text.entry")]
unsafe extern "C" fn _start() -> ! {
    core::arch::naked_asm!(
        // 1. 在需要时建立有效栈
        // 2. 在需要时清零 .bss、初始化 .data
        // 3. 调用 Rust 主程序
        // 4. 主程序若意外返回，进入安全的停止路径
    );
}
```

三个属性的意义：

1. `#[unsafe(naked)]`：不生成普通函数序言与尾声。
2. `#[unsafe(no_mangle)]`：保留 `_start` 这个导出符号名。
3. `#[unsafe(link_section = ".text.entry")]`：把函数放入指定的链接 section。

在一个自行建立栈的 x86-64 入口中，核心思路可能类似：

```asm
; 以下仅为指令意图，不是完整可链接代码
lea rsp, [rip + ...]    ; 取得预留栈空间的栈顶
and rsp, -16            ; 按调用约定要求准备对齐
; ...                   ; 初始化所需内存
call kernel_main        ; 转交给 Rust 主程序
; ...                   ; kernel_main 不应正常返回
```

这里需要注意：

- 栈空间必须实际存在，地址由链接脚本或其他可靠机制确定。
- `kernel_main` 的符号需要与汇编中的引用匹配。
- 是否需要搬运 `.data`、清零 `.bss`，取决于镜像布局和加载器已完成的工作。
- UEFI、Multiboot 等不同启动环境提供的初始状态不同。
- 对于不返回的 Rust 主函数，启动代码仍应设计合理的异常返回兜底路径。

而在 Cortex-M 上，Reset 时**硬件通常直接从向量表加载初始 MSP**，再进入 Reset Handler。`cortex-m-rt` 负责相应的启动支持；`set-sp` feature 还涉及额外的栈指针设置行为。

## 6. 总结：三个不同的层次

| 层次 | Cortex-M 方案 | x86-64 裸机方案 |
|---|---|---|
| 硬件架构 | ARMv6-M / ARMv7-M 等 | x86-64 |
| 初始执行机制 | Reset 时硬件读取向量表 | 固件、bootloader、启动协议决定 |
| Rust 启动支持 | `cortex-m-rt` | 自行实现或使用现成启动框架 |
| Rust 主程序入口 | `#[entry]` 标记的函数 | 启动代码转交给 Rust 主函数 |

最后区分三件事：

- **`no_std`**：Rust crate 不依赖标准库 `std`。
- **裸机运行**：程序不依赖常规操作系统提供的进程运行环境。
- **裸函数 / `naked_asm!`**：编译器不为函数生成常规序言和尾声，底层指令与函数边界由开发者控制。

**核心结论：** `no_std` 不等于裸机，裸机不等于必须写裸汇编。需要裸汇编的根本原因通常是：在某些极早期启动阶段，尚不能安全地依赖普通函数所假定的栈和调用环境。
