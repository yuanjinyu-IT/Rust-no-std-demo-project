# 从日志缓冲区出发，理解 Rust `no_std` 中的 `static`、`Cell`、`UnsafeCell`、`Sync` 与内存布局

> 这篇笔记以一个纯内存日志缓冲区 `LogBuffer<N>` 为主线，逐步解释为什么会引入 `static`、为什么需要内部可变性、为什么选择 `UnsafeCell` 而不是 `Cell`、为什么手动实现 `Sync`，最后重点讨论 `#[repr(transparent)]` 的实际用途。

我认为理解这些知识点最好的方法，不是分别记住它们的定义，而是沿着日志系统的设计过程，观察每一步遇到了什么问题，以及 Rust 提供了什么机制来解决它。

## 一、从最简单的日志缓冲区开始

### 1.1 我们究竟想实现什么？

假设正在开发一个 `no_std` 程序，希望实现日志输出，但暂时不考虑 UART、串口、屏幕等硬件设备。

我们希望能够这样使用：

``` rust
use core::fmt::Write;

let mut log = LogBuffer::<64>::new();

write!(log, "hello {}, answer = {}", "world", 42).unwrap();

assert_eq!(log.as_str(), "hello world, answer = 42");
```

这里的 `write!` 并不要求输出目标一定是终端或硬件设备。

它只需要目标实现：

``` rust
pub trait Write {
    fn write_str(&mut self, s: &str) -> core::fmt::Result;
}
```

也就是说，**格式化输出的本质，是把字符串交给某个实现了 `core::fmt::Write` 的对象。**

至于这个对象最终把数据写入串口、屏幕、文件还是内存，是它自己的实现细节。

因此，我们可以设计一个完全不依赖硬件的内存日志缓冲区。

### 1.2 设计 `LogBuffer<N>`

``` rust
pub struct LogBuffer<const N: usize> {
    buf: [u8; N],
    len: usize,
    dropped: usize,
}
```

三个字段分别承担不同职责：

| 字段             | 作用                     |
|------------------|--------------------------|
| `buf: [u8; N]`   | 固定容量的字节缓冲区     |
| `len: usize`     | 已写入的有效字节数       |
| `dropped: usize` | 因容量不足而丢弃的字节数 |

使用固定大小的数组意味着：

- 不需要堆分配。
- 不需要操作系统。
- 不需要任何输出硬件。
- 缓冲区容量在编译时确定。

`no_std` 并不意味着没有内存，而是不依赖标准库 `std`。这里需要的数组、字符串切片、格式化接口都可以通过 `core` 使用。

### 1.3 实现日志写入

下面是一份修正了 UTF-8 截断问题的实现：

``` rust
use core::fmt;

pub struct LogBuffer<const N: usize> {
    buf: [u8; N],
    len: usize,
    dropped: usize,
}

impl<const N: usize> LogBuffer<N> {
    pub const fn new() -> Self {
        Self {
            buf: [0; N],
            len: 0,
            dropped: 0,
        }
    }

    pub const fn len(&self) -> usize {
        self.len
    }

    pub const fn dropped(&self) -> usize {
        self.dropped
    }

    pub fn as_str(&self) -> &str {
        core::str::from_utf8(&self.buf[..self.len])
            .expect("LogBuffer must contain valid UTF-8")
    }
}

impl<const N: usize> fmt::Write for LogBuffer<N> {
    fn write_str(&mut self, s: &str) -> fmt::Result {
        let bytes = s.as_bytes();

        let mut n = core::cmp::min(
            bytes.len(),
            N - self.len,
        );

        // 不允许在 UTF-8 字符中间截断
        while !s.is_char_boundary(n) {
            n -= 1;
        }

        self.buf[self.len..self.len + n]
            .copy_from_slice(&bytes[..n]);

        self.len += n;

        self.dropped = self.dropped.saturating_add(
            bytes.len() - n
        );

        Ok(())
    }
}

impl<const N: usize> Default for LogBuffer<N> {
    fn default() -> Self {
        Self::new()
    }
}
```

这里有两个值得注意的设计。

**第一，缓冲区满了也返回 `Ok(())`。**

这是日志系统主动选择的策略：不希望因为日志写满而导致主程序失败。

但丢弃的数据会记录到 `dropped` 中，而不是完全静默丢弃。

**第二，必须保证 UTF-8 完整性。**

例如 `"你好"` 占 6 字节，如果缓冲区只能容纳 4 字节，就不能直接复制前 4 字节，否则会截断第二个汉字，破坏 UTF-8 编码。

使用 `is_char_boundary()` 可以保证只在完整字符边界处截断。

### 1.4 这个实现需要 `static`、`Cell` 或 `UnsafeCell` 吗？

答案是：**完全不需要。**

``` rust
let mut log = LogBuffer::<64>::new();
```

我们已经拥有一个可变的局部变量。

`write_str` 要求：

``` rust
fn write_str(&mut self, s: &str) -> fmt::Result;
```

而局部变量可以直接提供：

``` rust
&mut LogBuffer<64>
```

因此，普通的 Rust 可变借用就能完成所有工作。

这一步非常重要：

> `UnsafeCell` 不是因为 `no_std` 才需要的，`static` 也不是因为日志必须写入内存才需要的。只有当我们改变日志缓冲区的使用方式时，才会逐渐遇到这些概念。

## 二、为什么要引入 `static`？

### 2.1 局部日志的限制不是“不能写”，而是“不方便共享”

局部变量适合单独使用：

``` rust
fn run() {
    let mut log = LogBuffer::<1024>::new();
    // 在这里写日志
}
```

但如果初始化代码、主循环和错误处理代码都想写入**同一个**缓冲区，就需要把 `&mut LogBuffer` 层层传递：

``` rust
fn process(log: &mut LogBuffer<1024>) {
    use core::fmt::Write;
    write!(log, "processing").unwrap();
}
```

这种显式传参是完全合理的设计。如果不想每层都传递日志对象，则可以考虑全局实例：

``` rust
static LOG: LogBuffer<1024> = LogBuffer::new();
```

`static` 的价值是：**给数据一个在整个程序运行期间有效、可全局定位的存储位置**。它与“能不能修改数据”是两回事。

### 2.2 为什么直接定义的 `static LOG` 不能写？

上面的声明本身可以成立，因为 `LogBuffer<N>` 由数组和整数构成，自动满足 `Sync`。

但下面的思路不成立：

``` rust
// 不能直接把共享 static 当作 &mut LogBuffer 使用
// write!(LOG, "hello").unwrap();
```

原因在于 `fmt::Write` 需要 `&mut self`。普通共享 `static` 不允许直接获得可变引用。

这与 Rust 的引用规则有关：

| 引用     | 含义         | 核心约束                                   |
|----------|--------------|--------------------------------------------|
| `&T`     | 共享引用     | 允许多个共享访问，通常不能修改普通内部数据 |
| `&mut T` | 独占可变引用 | 在其有效的独占访问期间不能有冲突访问       |

于是产生新的设计问题：

> 我希望通过一个可以被全局共享的入口，修改同一份日志数据。Rust 允许这样做吗？

允许，但需要**内部可变性（Interior Mutability）**。

## 三、内部可变性：为什么不是直接用 `Cell`？

### 3.1 `Cell<T>` 确实能修改内部数据

`Cell<T>` 是 `core` 中的安全内部可变性容器：

``` rust
use core::cell::Cell;

let counter = Cell::new(0);
let shared = &counter;

shared.set(10);
assert_eq!(shared.get(), 10);
```

这里没有 `&mut Cell<i32>`，仍然可以通过 `&Cell<i32>` 修改内部值。

但它的设计重点是：**安全地替换或取出值，而不是通过共享引用借出内部的 `&mut T`**。

### 3.2 `Cell<LogBuffer<N>>` 可以使用，但不太适合频繁追加

``` rust
use core::cell::Cell;
use core::fmt::Write;

let cell = Cell::new(LogBuffer::<64>::new());

// take() 需要 LogBuffer 实现 Default
let mut log = cell.take();
write!(log, "hello").unwrap();
cell.set(log);
```

`take()` 会用默认值替换 `Cell` 内部的旧值，并返回旧值。这样做是安全的，但有代价：

1.  语义上需要把整个缓冲区移出、再放回；实际拷贝成本取决于优化。
2.  在取出和放回之间，`Cell` 内部暂时是一个新的空缓冲区。
3.  如果期间发生 panic 或重入，日志状态可能丢失或被覆盖。

`Cell::get_mut()` 也存在，但它需要 `&mut Cell<T>`，不能仅凭共享引用调用。

**一个容易忽略的细节：**`Cell<T>` 也有 `as_ptr()`，可以取得内部 `*mut T`。因此不是说 `Cell` 在技术上绝对无法支持原地修改；而是如果最终仍要依赖裸指针和 `unsafe`，直接使用底层的 `UnsafeCell` 更清晰。

### 3.3 `RefCell<T>` 呢？

`RefCell` 允许通过共享引用临时获取可变借用：

``` rust
use core::cell::RefCell;
use core::fmt::Write;

let log = RefCell::new(LogBuffer::<64>::new());
write!(&mut *log.borrow_mut(), "hello").unwrap();
```

它会在运行时检查借用规则。如果同一时刻发生冲突借用，会 panic。

这适合单线程中的共享可变状态，但 `RefCell<T>` 不实现 `Sync`，不能直接作为普通共享 `static` 的类型。

### 3.4 `UnsafeCell<T>` 的不同之处

`UnsafeCell<T>` 是 Rust 内部可变性的底层原语：

``` rust
use core::cell::UnsafeCell;
use core::fmt::Write;

let cell = UnsafeCell::new(LogBuffer::<64>::new());

let ptr: *mut LogBuffer<64> = cell.get();

unsafe {
    let log: &mut LogBuffer<64> = &mut *ptr;
    log.write_str("hello").unwrap();
}
```

注意这两步的区别：

- `cell.get()` **安全**：只取得裸指针，不访问数据。
- `&mut *ptr` **需要 `unsafe`**：必须证明这次可变访问合法。

`UnsafeCell` 放宽了共享引用对内部数据的通常不可变性保证，**但没有放宽独占可变引用的别名规则，也没有提供线程同步**。

因此：

| 工具              | 更适合什么场景                           | 是否自动线程安全         |
|-------------------|------------------------------------------|--------------------------|
| `Cell<T>`         | 计数器、标志位、整个值的替换             | 否                       |
| `RefCell<T>`      | 单线程中临时借用内部的 `&mut T`          | 否                       |
| `UnsafeCell<T>`   | 构建底层容器、锁或自行维护安全规则的抽象 | 否                       |
| 合适的 `Mutex<T>` | 多执行上下文安全访问共享可变状态         | 由具体实现与类型约束决定 |

所以，对于这份日志实现，作者选择 `UnsafeCell` 的原因是：

> 希望在不移出整个 `LogBuffer` 的情况下，直接获得原缓冲区的裸指针，并把后续访问是否合法的责任交给底层调用者。

## 四、为什么又需要 `Sync` 和 `unsafe impl Sync`？

### 4.1 `static` 对共享安全有要求

Rust 的两个标记 trait：

- `Send`：类型的值可以安全地在线程之间转移所有权。
- `Sync`：类型的共享引用可以安全地在线程之间共享。

准确关系是：

``` text
T: Sync  当且仅当  &T: Send
```

普通共享 `static` 要求其类型实现 `Sync`。

但是：

``` rust
UnsafeCell<LogBuffer<1024>>
```

**不实现 `Sync`**。`Cell<T>`、`RefCell<T>` 也都不实现 `Sync`。

为什么？因为它们支持内部可变性，却没有提供跨线程的同步保护。如果安全地共享这些容器并让多个线程同时修改内部数据，就可能发生数据竞争。

### 4.2 `SharedLog` 是怎样出现的？

于是作者定义一个包装类型：

``` rust
use core::cell::UnsafeCell;

#[repr(transparent)]
pub struct SharedLog<const N: usize>(
    UnsafeCell<LogBuffer<N>>
);

impl<const N: usize> SharedLog<N> {
    pub const fn new() -> Self {
        Self(UnsafeCell::new(LogBuffer::new()))
    }

    pub const fn get(&self) -> *mut LogBuffer<N> {
        self.0.get()
    }
}

// SAFETY:
// 这个类型暴露的安全操作仅能取得裸指针，
// 不能通过安全 Rust 解引用它来读写内部数据。
// 任何实际访问都需要调用者使用 unsafe 并遵守访问规则。
// 若以后增加安全的读写方法，必须重新证明同步安全。
unsafe impl<const N: usize> Sync for SharedLog<N> {}

static LOG: SharedLog<1024> = SharedLog::new();
```

这里的 `unsafe impl Sync` 不是加锁操作，而是程序员向 Rust 作出**共享引用可以安全跨线程使用**的承诺。

为什么这个受限的包装类型可以这样设计？

因为它目前公开的安全方法 `get()` 只返回裸指针。仅凭安全 Rust，调用者不能解引用它来读写日志。真正使用该指针必须进入 `unsafe`，并承担相应的安全前置条件。

这也是 `// SAFETY:` 注释应当解释的核心：**为什么这个类型的安全 API 不会让安全代码触发未定义行为？**

如果未来新增一个没有同步保护的安全方法：

``` rust
// 不能这样随意增加一个安全的共享写入方法：
// pub fn append(&self, s: &str) {
//     unsafe { (&mut *self.get()).write_str(s).unwrap(); }
// }
```

那么多个线程就可能通过安全 API 同时修改缓冲区，破坏 `Sync` 的安全承诺。

### 4.3 `unsafe impl Sync` 不等于“已经解决并发”

真实写入仍然需要保证独占访问：

``` rust
use core::fmt::Write;

/// # Safety
///
/// 调用者必须保证：
/// - 没有其他线程或中断处理程序冲突地访问 LOG；
/// - 不会发生递归或重入写入；
/// - 没有与本次可变引用冲突的现存引用。
unsafe fn append_unchecked(s: &str) {
    unsafe {
        let log = &mut *LOG.get();
        let _ = log.write_str(s);
    }
}
```

这里 `unsafe fn` 把前置条件写进函数契约；函数体中的 `unsafe` 块负责执行裸指针解引用。

尤其要注意：**只有一个 CPU 核心，也可能发生重入。**

``` text
主程序开始修改 LOG
        │
        ├── 中断发生
        │       └── 中断处理程序也修改 LOG
        │
        └── 中断返回，主程序继续执行
```

因此，单线程、单核、不使用操作系统，都不能自动证明这段访问是安全的。

如果需要提供一个真正安全的全局日志接口，应该在内部加入适合目标平台的同步机制，例如临界区或互斥锁，并认真处理中断重入。不能指望 `UnsafeCell` 或 `unsafe impl Sync` 自动完成这些工作。

## 五、最后理解 `#[repr(transparent)]`：它到底有什么实际用途？

这是整篇笔记最后一个问题，也是最容易被“内存对齐”这个概念掩盖的问题。

### 5.1 它保证的不只是内存对齐

先看一个例子：

``` rust
#[repr(transparent)]
struct StatusCode(u32);
```

这里的 `StatusCode` 是一个**新类型**，但它的唯一非零大小字段是 `u32`。

`#[repr(transparent)]` 保证这个包装类型与内部字段具有相同的：

1.  **大小（Size）**：占用多少字节。
2.  **对齐（Alignment）**：地址需要满足什么对齐要求。
3.  **布局（Layout）**：包装对象与被包装字段占据相同的内存位置。
4.  **ABI（Application Binary Interface）**：在函数调用、参数传递和返回值等二进制接口中，采用与内部字段兼容的表示和传递方式。

前三点涉及数据在内存中的样子；第四点则涉及**不同代码之间如何在二进制层面交换数据**。

例如：

``` text
u32
┌────────┬────────┬────────┬────────┐
│ Byte 0 │ Byte 1 │ Byte 2 │ Byte 3 │
└────────┴────────┴────────┴────────┘

StatusCode（repr transparent）
┌────────┬────────┬────────┬────────┐
│       内部的 u32，共 4 字节       │
└────────┴────────┴────────┴────────┘
```

这并不是说 Rust 把 `StatusCode` 和 `u32` 当成同一个类型。

``` rust
let code = StatusCode(7);

// 类型不同，不能直接赋值：
// let raw: u32 = code;

let raw: u32 = code.0; // 正确
```

**它们在类型系统中仍然不同，但在底层表示和 ABI 上有明确的兼容保证。**

### 5.2 真正的用途：保留类型安全，同时兼容底层 ABI

假设你需要调用一个 C 函数：

``` c
#include <stdint.h>

void report_status(uint32_t code);
```

C 函数希望收到一个 `uint32_t`。

在 Rust 中，你不想让业务代码到处使用裸 `u32`，因为普通整数可能代表状态码、设备编号、长度等不同含义。

于是设计一个新类型：

``` rust
#[repr(transparent)]
pub struct StatusCode(pub u32);
```

然后声明外部函数：

``` rust
unsafe extern "C" {
    fn report_status(code: StatusCode);
}

fn notify() {
    unsafe {
        report_status(StatusCode(7));
    }
}
```

这里 Rust 声明使用 `StatusCode`，而 C 函数接收 `uint32_t`。

之所以能够按同一 ABI 进行交互，就是因为 `repr(transparent)` 明确保证：**`StatusCode` 的 ABI 与内部 `u32` 一致。**

于是你同时得到了两个好处：

- 在 Rust 代码中，`StatusCode` 是独立类型，可以避免把不相关的整数混用。
- 在与 C 交互时，不需要额外的包装结构或不同的调用约定。

这就是 `repr(transparent)` 很有代表性的用途：**构建零额外包装开销、具有明确二进制兼容保证的新类型。**

以上 FFI 案例是对原笔记的补充，用来解释这一属性在实际工程中为何有价值。

### 5.3 那为什么不用 `#[repr(C)]`？

因为二者解决的问题不一样。

``` rust
#[repr(C)]
struct Point {
    x: u32,
    y: u32,
}
```

`repr(C)` 主要用于保证结构体遵循目标平台的 C 风格字段布局规则，例如字段顺序、填充和对齐。

而：

``` rust
#[repr(transparent)]
struct StatusCode(u32);
```

`repr(transparent)` 要保证的是：**整个包装类型与内部那个字段具有相同的布局和 ABI。**

这一区别在函数调用时很重要。

即使一个 `#[repr(C)]` 单字段结构体与 `u32` 的大小和对齐都相同，也不能在所有目标平台上假设“传递一个 C 结构体”与“传递一个整数”使用完全相同的 ABI。

因此：

| 属性                   | 主要解决的问题                                     |
|------------------------|----------------------------------------------------|
| 默认 `repr(Rust)`      | Rust 自行安排布局，不提供与包装字段 ABI 相同的保证 |
| `#[repr(C)]`           | 按 C 风格布局规则组织结构体                        |
| `#[repr(transparent)]` | 让包装类型与唯一非零大小字段拥有相同的布局和 ABI   |

这说明：**`repr(transparent)` 的价值不只是对齐，更重要的是包装类型与原始类型之间的二进制接口兼容性。**

### 5.4 回到 `SharedLog`：这里真的需要它吗？

再看最初的代码：

``` rust
#[repr(transparent)]
pub struct SharedLog<const N: usize>(
    UnsafeCell<LogBuffer<N>>
);
```

它保证：

``` text
SharedLog<N>
    │
    │ repr(transparent)：与内部字段布局、ABI 相同
    ▼
UnsafeCell<LogBuffer<N>>
    │
    │ UnsafeCell 本身也具有透明的内存表示
    ▼
LogBuffer<N>
```

但要注意两件事。

**第一，它没有让 `SharedLog` 变得线程安全。**

`Sync` 的安全契约、`UnsafeCell` 的内部可变性和 `repr(transparent)` 的布局保证完全是三回事。

**第二，它也没有固定 `LogBuffer` 内部字段的顺序。**

因为 `LogBuffer` 本身仍然使用默认的 Rust 布局：

``` rust
pub struct LogBuffer<const N: usize> {
    buf: [u8; N],
    len: usize,
    dropped: usize,
}
```

`repr(transparent)` 只保证外层包装与内层字段的布局一致，并不进一步规定 `buf`、`len`、`dropped` 在 `LogBuffer` 内部的偏移量。

因此不能仅仅因为加了 `repr(transparent)`，就认为整个日志缓冲区适合直接作为跨语言的稳定二进制结构或持久化文件格式。

还有一个底层细节：虽然 `UnsafeCell<T>` 与 `T` 具有相同的内存表示，但 `UnsafeCell` 可能影响外层类型的 niche 优化。所以不能由此推断 `Option<UnsafeCell<T>>` 和 `Option<T>` 一定具有相同大小。

### 5.5 所以，在这个例子中去掉它可以吗？

**可以。**

``` rust
pub struct SharedLog<const N: usize>(
    UnsafeCell<LogBuffer<N>>
);
```

对于当前的日志实现，如果只是：

- 把它放进 `static`；
- 调用 `get()` 取得内部裸指针；
- 在满足安全前置条件时访问 `LogBuffer`；

那么并没有依赖 `repr(transparent)` 所提供的布局或 ABI 保证。

去掉它不会改变 `UnsafeCell` 的内部可变性机制，也不会改变手动实现 `Sync` 所承担的安全责任。

只有当你明确需要包装类型与内部类型在底层二进制表示上兼容，例如 FFI 或经过审查的底层指针接口时，这个属性才真正体现出用途。即使布局兼容，也仍然必须遵守指针有效性、别名和访问权限规则。

## 六、把整个设计过程重新串起来

``` text
需求：把格式化日志写进内存
    │
    ▼
LogBuffer<N> + core::fmt::Write
    │
    │ 已经有 &mut LogBuffer
    │ → 不需要 Cell、UnsafeCell 或 static
    │
    ▼
需求变化：多个函数想访问同一个长期存在的日志
    │
    ▼
static
    │
    │ 解决存储生命周期和全局访问
    │ 但不能直接提供 &mut LogBuffer
    │
    ▼
需要内部可变性
    │
    ├── Cell：安全的值替换，不适合频繁移出整个缓冲区
    │
    ├── RefCell：运行时检查借用，但不是 Sync
    │
    └── UnsafeCell：提供底层可变裸指针
              │
              ▼
          SharedLog<N>
              │
              │ 普通共享 static 要求 Sync
              ▼
          unsafe impl Sync
              │
              │ 只是安全契约，不是同步机制
              ▼
          调用方独占访问 / 锁 / 临界区
              │
              ▼
          真正安全地访问共享日志
```

而 `#[repr(transparent)]` 并不处在这条“如何安全写日志”的必经路径上。

它是另一个维度的设计选择：

``` text
需要一个独立的包装类型
          │
          ▼
希望保留内部类型的布局和 ABI
          │
          ▼
#[repr(transparent)]
```

最后用一张表区分所有概念：

| 概念                   | 解决什么问题                   | 不解决什么问题         |
|------------------------|--------------------------------|------------------------|
| `LogBuffer<N>`         | 日志存储和格式化写入           | 全局共享和同步         |
| `static`               | 全局位置和程序运行期存储       | 可变访问               |
| `Cell<T>`              | 共享引用下安全替换内部值       | 线程安全               |
| `RefCell<T>`           | 运行时可变借用检查             | 跨线程同步             |
| `UnsafeCell<T>`        | 底层内部可变性                 | 独占访问和同步         |
| `Send`                 | 所有权跨线程转移               | 共享引用安全           |
| `Sync`                 | 共享引用跨线程安全的契约       | 自动加锁               |
| `unsafe impl Sync`     | 手动承担并证明 `Sync` 契约     | 自动验证安全性         |
| `#[repr(transparent)]` | 包装类型与字段的布局、ABI 兼容 | 可变性、同步或线程安全 |

**最终结论：**

设计 `LogBuffer` 时，我们只是在解决“日志写到哪里”；引入 `static` 后，才需要思考“如何访问同一份数据”；引入 `UnsafeCell` 后，必须思考“谁保证修改是合法的”；实现 `Sync` 后，还必须保证共享接口不会破坏内存安全。

而 `#[repr(transparent)]` 解决的是另一类问题：**当我们创建一个新的 Rust 类型来包装已有类型时，如何保证这个包装不会改变底层布局和函数调用 ABI。**

这正是它的实际意义，也是为什么在当前这个纯内存日志例子中，它可以存在，却并非必需。
