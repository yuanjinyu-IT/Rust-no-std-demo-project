## 0. 一张图看完整知识链

``` text
用户程序调用 sys_write()
    │
    ├─ Rust 切片 &[u8] → 指针 + 长度
    │
    ├─ 按系统调用 ABI 把编号和参数放入寄存器
    │
    └─ 执行 syscall / svc #0 / ecall
                       │
                       ▼
                 CPU 进入内核
                       │
              保存用户 TrapContext
                       │
                 内核处理请求
                       │
           ┌───────────┴────────────┐
           │                        │
       直接返回                 需要调度
           │                        │
     更新返回值 a0          保存 TaskContext A
           │                恢复 TaskContext B
     恢复用户现场                   │
           │                恢复任务 B 的用户现场
           └───────────┬────────────┘
                       │
                sret 返回用户态
```

**核心区分**：

-   **ABI**：约定参数、返回值如何通过寄存器传递。
-   **Trap**：CPU 因异常、中断或环境调用进入处理程序的机制。
-   **`TrapContext`**：保存被 Trap 打断的执行现场。
-   **`TaskContext`**：保存任务在内核中切换所需的执行现场。
-   **`__switch`**：在两个内核任务上下文之间切换。
-   **`sret`**：按照 CSR 状态从 S-mode Trap 处理路径返回。

## 1. Rust 系统调用练习：从 `sys_write` 开始

### 1.1 系统调用是什么？

普通用户程序不能随意执行特权操作。它需要通过系统调用向操作系统请求服务，例如：

  系统调用   作用
  ---------- -----------------------------------------------------------
  `read`     从文件描述符读取数据
  `write`    向文件描述符写入数据
  `close`    关闭文件描述符
  `exit`     结束调用进程/线程的相应执行路径（具体语义取决于系统调用）

系统调用不是普通的 Rust 函数调用：它涉及架构规定的指令和操作系统 ABI。

### 1.2 x86_64 Linux 的 `syscall3`

``` rust
#[cfg(all(target_arch = "x86_64", target_os = "linux"))]
pub unsafe fn syscall3(
    id: usize,
    arg0: usize,
    arg1: usize,
    arg2: usize,
) -> isize {
    let ret: isize;
    unsafe {
        core::arch::asm!(
            "syscall",
            inlateout("rax") id => ret,
            in("rdi") arg0,
            in("rsi") arg1,
            in("rdx") arg2,
            out("rcx") _,
            out("r11") _,
        );
    }
    ret
}
```

逐行理解：

-   `"syscall"`：执行 x86_64 系统调用入口指令。
-   `inlateout("rax") id => ret`：进入前 `rax` 保存系统调用号，返回后从
    `rax` 读取结果。
-   `in("rdi") arg0`、`in("rsi") arg1`、`in("rdx") arg2`：放置前三个参数。
-   `out("rcx") _`、`out("r11") _`：告诉编译器，这两个寄存器会被指令覆盖。
-   `unsafe`：调用者需要保证该低级操作满足相关安全前提；`unsafe`
    并不会自动让操作变安全。

### 1.3 四个包装函数

``` rust
pub fn sys_write(fd: usize, buf: &[u8]) -> isize {
    unsafe {
        syscall3(
            NATIVE_SYS_WRITE,
            fd,
            buf.as_ptr() as usize,
            buf.len(),
        )
    }
}

pub fn sys_read(fd: usize, buf: &mut [u8]) -> isize {
    unsafe {
        syscall3(
            NATIVE_SYS_READ,
            fd,
            buf.as_mut_ptr() as usize,
            buf.len(),
        )
    }
}

pub fn sys_close(fd: usize) -> isize {
    unsafe { syscall3(NATIVE_SYS_CLOSE, fd, 0, 0) }
}

pub fn sys_exit(code: i32) -> ! {
    unsafe {
        syscall3(NATIVE_SYS_EXIT, code as usize, 0, 0);
    }
    panic!("sys_exit unexpectedly returned");
}
```

要点：

-   `&[u8]`：借用一段只读字节数据，适合 `write`。
-   `&mut [u8]`：借用可写字节缓冲区，适合 `read`。
-   `.as_ptr()` / `.as_mut_ptr()`：取得切片起始元素的原始指针。
-   `.len()`：取得切片的元素数；对 `[u8]` 来说也就是字节数。
-   `as usize`：按 ABI 需要把地址转换为整数形式；**不复制缓冲区内容**。
-   `!`：函数正常情况下不返回。
-   `sys_exit` 中的 `panic!` 是异常返回的兜底；真实 `exit`
    系统调用正常情况下不会返回。Linux x86_64 的 `exit`
    系统调用通常终止当前线程；进程组退出还涉及 `exit_group`。

## 2. Rust 内存基础：引用、指针、切片

### 2.1 内存地址

内存按字节编址。假设 `"Hello"` 从地址 `0x1000` 开始：

``` text
地址       字节
0x1000     'H'
0x1001     'e'
0x1002     'l'
0x1003     'l'
0x1004     'o'
```

这些地址仅用于示意；实际程序中的指针通常表示**虚拟地址**。

### 2.2 引用与裸指针

``` rust
let data = [10u8, 20, 30];
let slice: &[u8] = &data;
let ptr: *const u8 = slice.as_ptr();
```

  类型         含义
  ------------ ----------------------------------------
  `&T`         共享引用，受 Rust 有效性与借用规则约束
  `&mut T`     可变引用，具有相应独占访问保证
  `*const T`   原始只读指针，不自动保证可以安全解引用
  `*mut T`     原始可变指针，不自动保证可以安全写入

裸指针转换本身可以是安全的，但**解引用裸指针需要
`unsafe`，且必须满足有效地址、对齐、权限等前提**。

### 2.3 切片为什么能拆成指针与长度？

``` rust
let buf: &[u8] = b"Hello";

let address = buf.as_ptr() as usize;
let length = buf.len();
```

从概念上看，切片引用包含：

``` text
&[u8]
├── 起始指针
└── 元素长度
```

Linux `write(fd, buf, count)` 正好需要文件描述符、缓冲区地址和字节数。

**注意**：把指针转换成整数并不等于任意整数都可以安全地重新转换成指针并解引用；Rust
的指针来源与有效性规则仍然适用。

## 3. 用户态、内核态与 CPU 特权级

### 3.1 为什么需要特权级？

如果普通程序可以随意访问其他进程的内存、修改系统控制寄存器或操纵设备，操作系统就无法提供可靠的隔离和保护。

常见的权限划分：

  架构      普通用户程序   操作系统内核
  --------- -------------- --------------
  x86_64    Ring 3         Ring 0
  AArch64   EL0            EL1
  RISC-V    U-mode         S-mode

RISC-V 还定义 M-mode（机器模式），常用于更底层的固件或运行环境。

### 3.2 执行系统调用时发生什么？

1.  用户程序按照 ABI 准备寄存器。
2.  执行系统调用入口指令。
3.  CPU 根据架构规则进入异常/特权处理路径。
4.  内核入口保存必要状态，建立可靠的内核执行环境。
5.  内核判断系统调用编号、检查参数并执行服务。
6.  内核设置返回值、恢复必要状态，返回用户程序。

**关键细节**：CPU
的入口指令通常**不会自动保存全部通用寄存器，也不会自动替内核完成全部栈切换工作**。

### 3.3 System Call、Exception、Interrupt、Trap

  ----------------------------------------------------------------------------------------------
  概念                    说明                                           例子
  ----------------------- ---------------------------------------------- -----------------------
  System Call             用户程序主动请求内核服务                       `write`

  Exception               与当前指令执行同步的异常事件                   非法指令、缺页

  Interrupt               通常来自外部的异步事件                         定时器中断

  Trap                    OS                                             `ecall` 导致的陷入
                          教学中常用于描述异常或中断进入处理程序的过程   
  ----------------------------------------------------------------------------------------------

## 4. 三种架构的 Linux 系统调用 ABI

**ABI（Application Binary Interface）**规定了二进制接口的约定。系统调用
ABI 决定了系统调用号、参数和返回值所使用的寄存器。

### 4.1 对照表

  项目           x86_64      AArch64    RISC-V 64
  -------------- ----------- ---------- -----------
  入口指令       `syscall`   `svc #0`   `ecall`
  系统调用号     `rax`       `x8`       `a7`
  参数 1         `rdi`       `x0`       `a0`
  参数 2         `rsi`       `x1`       `a1`
  参数 3         `rdx`       `x2`       `a2`
  参数 4         `r10`       `x3`       `a3`
  参数 5         `r8`        `x4`       `a4`
  参数 6         `r9`        `x5`       `a5`
  返回值         `rax`       `x0`       `a0`
  `read` 编号    0           63         63
  `write` 编号   1           64         64
  `close` 编号   3           57         57
  `exit` 编号    60          93         93

### 4.2 AArch64 寄存器与 `svc #0`

AArch64 的 64 位通用寄存器通常命名为 `x0`--`x30`，另有 `sp`。在 Linux
系统调用 ABI 中：

-   `x8`：系统调用编号。
-   `x0`--`x5`：前六个系统调用参数。
-   `x0`：返回值。

示例：

``` rust
#[cfg(all(target_arch = "aarch64", target_os = "linux"))]
pub unsafe fn syscall3(
    id: usize,
    arg0: usize,
    arg1: usize,
    arg2: usize,
) -> isize {
    let ret: isize;
    unsafe {
        core::arch::asm!(
            "svc #0",
            in("x8") id,
            inlateout("x0") arg0 => ret,
            in("x1") arg1,
            in("x2") arg2,
        );
    }
    ret
}
```

`svc #0` 会产生同步异常；典型 Linux 用户程序从 EL0 进入 EL1
内核处理路径。

### 4.3 RISC-V 寄存器与 `ecall`

RISC-V RV64 有 32 个整数寄存器 `x0`--`x31`，并为它们规定 ABI 别名。

  寄存器         别名          常见作用
  -------------- ------------- --------------------
  `x0`           `zero`        恒为零
  `x1`           `ra`          返回地址
  `x2`           `sp`          栈指针
  `x5`--`x7`     `t0`--`t2`    临时寄存器
  `x8`--`x9`     `s0`--`s1`    被调用者保存寄存器
  `x10`--`x17`   `a0`--`a7`    函数参数、返回值等
  `x18`--`x27`   `s2`--`s11`   被调用者保存寄存器
  `x28`--`x31`   `t3`--`t6`    临时寄存器

Linux RISC-V 的系统调用：

``` asm
li a7, 64       # write
li a0, 1        # stdout
la a1, message  # 缓冲区地址
li a2, 5        # 长度
ecall
```

`ecall` 负责触发环境调用异常；**具体执行哪种服务，由操作系统依据 `a7`
的值决定**。

扩展示例：

``` rust
#[cfg(all(target_arch = "riscv64", target_os = "linux"))]
pub unsafe fn syscall3(
    id: usize,
    arg0: usize,
    arg1: usize,
    arg2: usize,
) -> isize {
    let ret: isize;
    unsafe {
        core::arch::asm!(
            "ecall",
            in("a7") id,
            inlateout("a0") arg0 => ret,
            in("a1") arg1,
            in("a2") arg2,
        );
    }
    ret
}
```

**区分**：上面是 **RISC-V Linux 用户态 ABI**。自己编写的裸机 OS
可以定义自己的系统调用编号和参数规则，不能直接假设所有内核都使用 Linux
编号。

## 5. Rust 内联汇编的寄存器约束与副作用

### 5.1 `in`、`out`、`inlateout`

``` rust
in("a7") id
```

执行前将 `id` 放入 `a7`。

``` rust
inlateout("a0") arg0 => ret
```

执行前把 `arg0` 放入 `a0`；执行后从 `a0` 读取结果到 `ret`。

``` rust
out("rcx") _
```

告诉编译器该寄存器会被覆盖，原值不能被假定保留。

### 5.2 为什么 x86_64 要声明 `rcx` 和 `r11`？

x86_64 的 `syscall` 指令会覆盖 `rcx` 和
`r11`。若编译器不知道这一点，可能错误地认为其中的旧数据仍然有效。

因此：

``` rust
out("rcx") _,
out("r11") _,
```

是必要的寄存器副作用声明。

### 5.3 为什么通用 `syscall3` 不能声明 `nomem`？

`options(nomem)` 表示汇编不会读取或写入内存。

但：

-   `write` 可能读取用户缓冲区。
-   `read` 可能写入用户缓冲区。

因此，给通用系统调用包装添加 `nomem`
会错误描述其内存副作用，可能破坏编译器优化所依赖的假设。

其他选项，例如
`nostack`、`preserves_flags`，也必须在确实满足对应条件时才能声明。

## 6. RISC-V Trap 的完整流程

### 6.1 `ecall` 触发了什么？

在常见的 RISC-V 教学内核中，U-mode 用户程序执行 `ecall` 后，异常进入
S-mode Trap 处理路径。

``` text
U-mode 用户程序
    │
    └─ ecall
         │
         ▼
CPU 记录 Trap 原因和返回状态
         │
         ▼
S-mode Trap 入口汇编
         │
         ├─ 安排内核栈
         ├─ 保存用户寄存器
         └─ 调用 Rust Trap Handler
                   │
                   ▼
              处理系统调用
                   │
                   ▼
              恢复用户现场
                   │
                   ▼
                  sret
                   │
                   ▼
            U-mode 继续执行
```

CPU 硬件不会自动保存所有通用寄存器；内核入口必须自行处理。

### 6.2 四个关键 CSR

CSR 是 **Control and Status Register（控制与状态寄存器）**。

  CSR         作用
  ----------- ----------------------------
  `stvec`     S-mode Trap 入口地址与模式
  `sepc`      记录 Trap 对应的指令地址
  `scause`    记录 Trap 原因
  `sstatus`   保存和控制 S-mode 相关状态

额外重要的 CSR：

-   `sscratch`：供 S-mode 软件暂存数据，常用于 Trap 入口设计。

### 6.3 `sepc` 为什么通常要加 4？

对 U-mode `ecall` 异常，`sepc` 记录的是 **`ecall` 指令本身**的地址。

例如：

``` text
0x1000: 准备参数
0x1004: ecall
0x1008: 下一条指令
```

异常发生时：

``` text
sepc = 0x1004
```

如果返回前不调整，可能再次执行同一条 `ecall`。

因为 RISC-V `ecall` 指令长度为 4
字节，内核处理完此类系统调用后通常执行：

``` rust
trap_cx.sepc += 4;
```

使返回位置指向 `0x1008`。

这不是说**所有** Trap 都应当把 `sepc` 加 4。不同异常和中断需要不同处理。

### 6.4 `scause` 和 `sstatus`

-   来自 U-mode 的环境调用异常，其异常原因编码为 `8`。
-   `sstatus.SPP` 记录 Trap 之前的特权模式信息。
-   `sstatus.SPIE` 保存与中断使能相关的状态，供异常返回恢复使用。

## 7. `TrapContext`：保存用户程序的现场

### 7.1 为什么需要它？

内核处理 Trap 时会使用 CPU
寄存器。如果不保存用户原有状态，返回用户态后程序可能无法正确继续执行。

典型教学结构：

``` rust
#[repr(C)]
pub struct TrapContext {
    pub x: [usize; 32],
    pub sstatus: usize,
    pub sepc: usize,
}
```

其中：

``` text
x[1]  ↔ ra
x[2]  ↔ sp
x[10] ↔ a0
x[11] ↔ a1
x[12] ↔ a2
x[17] ↔ a7
```

`x0`
恒为零，因此实际保存时可以不需要保存其值，但数组仍可保留位置方便索引。

`#[repr(C)]` 使结构体采用目标平台的 C
兼容布局规则，便于汇编使用固定偏移访问字段。

### 7.2 系统调用处理示例

``` rust
fn handle_user_ecall(cx: &mut TrapContext) {
    cx.sepc += 4;

    let id = cx.x[17];    // a7
    let arg0 = cx.x[10];  // a0
    let arg1 = cx.x[11];  // a1
    let arg2 = cx.x[12];  // a2

    let result = syscall(id, arg0, arg1, arg2);

    cx.x[10] = result as usize;
}
```

> 这是教学伪代码：`syscall`
> 代表自定义内核的系统调用分发函数，并非可直接编译的完整实现。

内核将返回值写入 `cx.x[10]`，之后恢复寄存器时，用户程序就能从 `a0`
读到结果。

## 8. 用户栈、内核栈与 `sscratch`

### 8.1 栈是什么？

栈是一块按约定管理的内存区域，用于函数调用、局部数据、保存寄存器等。

RISC-V 常见 ABI 下，栈向低地址增长：

``` asm
addi sp, sp, -16  # 预留 16 字节
addi sp, sp, 16   # 释放 16 字节
```

### 8.2 为什么区分用户栈和内核栈？

用户栈由用户任务使用，可能无效、空间不足或被恶意构造。内核执行时需要可靠的栈，因此教学内核通常为任务准备独立的内核栈。

**RISC-V Trap 硬件不会自动切换 `sp`。**

### 8.3 `sscratch` 与 `csrrw`

一种教学设计会让 `sscratch` 暂存内核栈地址。

``` asm
csrrw sp, sscratch, sp
```

其作用是交换 `sp` 和 `sscratch` 的旧值。

``` text
执行前：
sp       = 0x2000  （用户栈）
sscratch = 0x9000  （内核栈）

执行后：
sp       = 0x9000  （内核栈）
sscratch = 0x2000  （用户栈）
```

这能在不丢失用户栈指针的情况下切换到内核栈。

**注意**：真实内核可能让 `sscratch` 保存 TrapContext
指针等其他数据；从内核态再次发生 Trap
时也必须有额外处理，不能不加判断地执行同一交换逻辑。

## 9. Trap 入口与恢复：`__alltraps`、`__restore`、`sret`

### 9.1 保存现场的汇编指令

RV64 常见指令：

``` asm
sd ra, 8(sp)  # 将 64 位 ra 保存到内存
ld ra, 8(sp)  # 从内存恢复 64 位 ra
```

`sd` 是 **Store Doubleword**，`ld` 是 **Load Doubleword**。

教学内核的 Trap 入口大致需要：

1.  获取可靠的内核执行环境。
2.  保存用户通用寄存器。
3.  保存 `sepc`、`sstatus` 等必要状态。
4.  把 TrapContext 指针交给 Rust Handler。

伪代码：

``` asm
__alltraps:
    # 取得内核栈并保留用户 sp
    # 分配 TrapContext 空间
    # sd 保存必要的通用寄存器
    # 读取 CSR 并保存
    # 调用 Rust trap_handler
```

这是流程示意，不是可直接运行的完整汇编。

### 9.2 `__restore` 做什么？

处理完成后，恢复代码需要：

1.  把保存的 `sepc`、`sstatus` 写回相应 CSR。
2.  从 TrapContext 恢复通用寄存器。
3.  恢复用户栈指针。
4.  执行 `sret`。

### 9.3 `sret` 做什么？

`sret` 是 Supervisor Return。

它根据 `sepc`、`sstatus` 等状态恢复 Trap 返回所需的控制流与特权状态。

例如，`SPP=0` 时可返回 U-mode，程序计数器从 `sepc` 指定的位置继续。

**`sret` 不会自动恢复所有通用寄存器**；那是恢复汇编的工作。

------------------------------------------------------------------------

## 10. `TaskContext`：为什么任务切换只保存 14 个寄存器？

### 10.1 与 `TrapContext` 的区别

  ---------------------------------------------------------------------------------------
  项目                    `TrapContext`                         `TaskContext`
  ----------------------- ------------------------------------- -------------------------
  保存对象                被 Trap 打断的执行现场                内核任务切换现场

  常见内容                大部分通用寄存器、`sepc`、`sstatus`   `ra`、`sp`、`s0`--`s11`

  典型使用                Trap 入口与返回                       `__switch`

  典型返回                `sret`                                `ret`
  ---------------------------------------------------------------------------------------

### 10.2 Caller-saved 与 Callee-saved

RISC-V 函数调用 ABI 把寄存器分成：

-   **Caller-saved（调用者保存）**：`a0`--`a7`、`t0`--`t6`
    等。调用者若要保留值，应自行保存。
-   **Callee-saved（被调用者保存）**：`s0`--`s11`。被调用函数若使用它们，应在返回前恢复。
-   `sp`：必须保持符合 ABI 的栈状态。
-   `ra`：普通函数调用的返回地址寄存器，任务切换需要额外保存。

因为 `__switch` 被设计成符合普通函数调用 ABI
的汇编函数，所以通常只保存：

``` rust
#[repr(C)]
pub struct TaskContext {
    pub ra: usize,
    pub sp: usize,
    pub s: [usize; 12],
}
```

`ra` + `sp` + 12 个 `s` 寄存器，共 14 个寄存器值。

**重要前提**：这是在函数调用边界进行的内核任务切换，不能用这 14
个寄存器替代异步 Trap 的完整现场保存。

------------------------------------------------------------------------

## 11. `__switch`：保存 A，恢复 B

### 11.1 函数声明

``` rust
unsafe extern "C" {
    fn __switch(
        current: *mut TaskContext,
        next: *const TaskContext,
    );
}
```

RISC-V 函数调用 ABI 规定：

``` text
a0 = current
a1 = next
```

### 11.2 RV64 汇编示例

``` asm
.globl __switch
__switch:
    # 保存当前任务
    sd ra, 0(a0)
    sd sp, 8(a0)
    sd s0, 16(a0)
    sd s1, 24(a0)
    sd s2, 32(a0)
    sd s3, 40(a0)
    sd s4, 48(a0)
    sd s5, 56(a0)
    sd s6, 64(a0)
    sd s7, 72(a0)
    sd s8, 80(a0)
    sd s9, 88(a0)
    sd s10, 96(a0)
    sd s11, 104(a0)

    # 恢复下一个任务
    ld ra, 0(a1)
    ld sp, 8(a1)
    ld s0, 16(a1)
    ld s1, 24(a1)
    ld s2, 32(a1)
    ld s3, 40(a1)
    ld s4, 48(a1)
    ld s5, 56(a1)
    ld s6, 64(a1)
    ld s7, 72(a1)
    ld s8, 80(a1)
    ld s9, 88(a1)
    ld s10, 96(a1)
    ld s11, 104(a1)

    ret
```

为什么 `ret` 可以切换任务？

因为 `__switch` 已经把 `ra` 替换成**任务 B 保存的返回地址**。

``` text
切换前：
CPU 的 ra、sp、s0... = 任务 A 的状态

保存：
TaskContext A ← CPU 寄存器

恢复：
CPU 寄存器 ← TaskContext B

ret：
跳转到任务 B 保存的 ra
```

因此，任务 A 的调用不会立即返回；它可能等到以后重新被调度时，才从原来的
`__switch` 调用位置继续执行。

### 11.3 新任务第一次运行怎么办？

新任务从未被切换出去，没有历史上下文。内核可以为它构造初始
`TaskContext`：

``` rust
impl TaskContext {
    pub fn goto_trap_return(kernel_stack_top: usize) -> Self {
        Self {
            ra: trap_return as usize,
            sp: kernel_stack_top,
            s: [0; 12],
        }
    }
}
```

这里 `trap_return`
代表教学内核预先准备的入口符号；该示例不是独立可编译程序。

当任务第一次被恢复时，`ret` 会跳到这个入口。

## 12. 调度器如何在任务之间切换？

`__switch` 负责**执行切换**，但不负责**选择任务**。

选择下一个任务的是调度器（Scheduler）。

### 12.1 常见任务状态

  状态      含义
  --------- ------------------------
  Ready     准备好运行，等待 CPU
  Running   正在运行
  Blocked   等待事件，暂时不能运行
  Exited    已结束

简单的轮转调度策略：

``` text
A → B → C → A → B → C ...
```

但如果 C 正在等待输入，调度器通常不会选择 C 运行。

### 12.2 调度过程

``` rust
fn schedule() {
    let current = current_task();
    let next = find_next_ready_task();

    // 更新任务状态和调度队列

    unsafe {
        __switch(
            current.task_context_ptr(),
            next.task_context_ptr(),
        );
    }
}
```

这只是教学伪代码。真实内核还需要管理任务所有权、锁、调度队列及上下文生命周期。

### 12.3 定时器中断引发任务切换

``` text
任务 A 在用户态运行
    │
    ▼
定时器中断发生
    │
    ▼
Trap 入口保存 A 的 TrapContext
    │
    ▼
内核调度器决定运行 B
    │
    ▼
__switch 保存 A 的 TaskContext
    │
    ▼
__switch 恢复 B 的 TaskContext
    │
    ▼
B 从此前的内核执行位置继续
    │
    ▼
恢复 B 的 TrapContext
    │
    ▼
sret 返回 B 的用户态
```

这里存在两层现场：

1.  **用户现场**：由 TrapContext 保存。
2.  **内核任务现场**：由 TaskContext 保存。

### 12.4 `ret` 和 `sret` 的区别

  指令     主要用途                       特权级
  -------- ------------------------------ ---------------------------
  `ret`    按 `ra` 返回普通函数调用位置   指令本身不改变特权级
  `sret`   从 S-mode Trap 处理路径返回    根据相关 CSR 恢复特权状态

因此：

-   `__switch` 最后的 `ret`，通常恢复另一个任务的**内核执行现场**。
-   后续的 `sret`，才负责按 Trap 返回状态进入用户态。

## 13. 常见易混淆问题

**Q1：`syscall3()` 和内核的 `syscall()` 分发函数是同一个东西吗？**

不是。前者是用户态包装，负责按 ABI
触发系统调用；后者是自定义内核中的处理逻辑，负责解释编号并执行服务。

**Q2：`ecall` 是否一定调用 Linux？**

不是。`ecall` 是 RISC-V
架构指令，具体由哪一层环境处理、使用何种系统调用编号，取决于运行环境和操作系统设计。

**Q3：`TrapContext` 是否一定放在内核栈上？**

不一定。教学内核可能放在内核栈或单独的 TrapContext 区域，取决于实现。

**Q4：`__switch` 会自动切换用户态和内核态吗？**

不会。它通常是内核内部的上下文切换函数，最后通过普通 `ret`
继续另一个内核执行现场。

**Q5：`sret` 会自动恢复 `a0`、`sp`、`ra` 吗？**

不会。通用寄存器需要内核恢复汇编处理。

**Q6：为什么系统调用之后 `a0` 可能变化？**

因为 ABI 明确规定 `a0` 是返回值寄存器。内核会把结果写入保存的 `a0`。

**Q7：为什么内核栈不能直接用用户栈代替？**

因为用户栈可能不可靠，内核需要有受控的执行环境，而且 RISC-V
硬件不会自动替换 `sp`。

**Q8：为什么 `TaskContext` 不保存 `a0`--`a7`？**

因为这里的 `__switch` 遵循普通函数调用
ABI，调用者保存寄存器的必要值由调用代码负责。异步 Trap
仍需保存更完整的现场。

## 15. 最后复习：必须记住的 12 句话

1.  **系统调用**是用户程序向内核请求服务的机制。
2.  **ABI**决定系统调用号、参数和返回值放在哪些寄存器。
3.  Rust 的**切片**可以提供指针和长度，但指针本身不保证访问安全。
4.  x86_64 使用 `syscall`，AArch64 使用 `svc #0`，RISC-V 使用 `ecall`。
5.  RISC-V Linux 用 `a7` 传递系统调用号，用 `a0` 接收返回值。
6.  **Trap**让 CPU 转入异常或中断处理路径。
7.  `sepc` 保存异常返回相关地址；处理 `ecall` 后通常要跳过该指令。
8.  **TrapContext**保存被打断的用户执行现场。
9.  RISC-V Trap 硬件**不会自动保存全部通用寄存器或切换内核栈**。
10. **TaskContext**通常保存 `ra`、`sp`、`s0`--`s11`。
11. **调度器决定切给谁，`__switch` 负责真正切换**。
12. **`ret` 恢复普通函数执行路径；`sret` 完成 Trap 返回**。
